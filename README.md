# Helix

**AI-native project-based CRM** — CRM, в которой каждый лид не строка в таблице, а полноценный проект-воркспейс: канбан-фазы сделки, страницы с описанием, база знаний, файлы, задачи, контакты и персональный RAG-чат с ИИ, который отвечает строго в контексте этого конкретного лида. Продукт создаётся по вехам M0–M6, соло.

## Идея

Классические CRM моделируют лид как запись с полями. Helix моделирует лид как **проект** — вокруг него собирается вся история: переписка, документы, вложения, задачи, изменения статуса. AI-ассистент встроен не поверх интерфейса, а на уровне данных: у каждого проекта есть свой RAG-чат, который видит контекст именно этого лида (историю активности, страницы, файлы, KB) и ничего лишнего — ни чужих лидов, ни чужих организаций.

## Технологический стек

**Backend** (`apps/api`)
- NestJS + TypeScript (strict mode)
- PostgreSQL 17 + Prisma ORM, pgvector (векторный поиск с M4)
- Zod — единственный источник контрактов API (`packages/api-schemas`), без class-validator/DTO-классов
- CASL — policy-guards для авторизации на каждом эндпоинте
- Redis + BullMQ — асинхронные очереди (email, RAG-индексация, maintenance-джобы)
- AWS S3 / MinIO — хранилище файлов через presigned URL

**Frontend** (`apps/web`, с M1)
- Vite + React
- TanStack Router (файловая маршрутизация) + TanStack Query (server state)
- Zustand — только UI-состояние
- Tailwind CSS + shadcn/ui (Radix + CVA) — общая дизайн-система в `packages/ui`
- dnd-kit (канбан), TipTap (редактор страниц)

**AI / RAG**
- Chunking → embeddings → pgvector (HNSW-индекс, cosine similarity) → retrieval, заскоуленный по организации и проекту
- Tool calling — AI-ассистент предлагает действия (сменить фазу, создать задачу), но выполняет их только через существующий сервисный слой после подтверждения пользователя и повторной проверки прав

**Инфраструктура**
- Render (API), Vercel (фронтенд), Supabase (Postgres), Upstash (Redis)
- pnpm workspaces + Turborepo — монорепозиторий

## Структура монорепозитория

```
apps/
  api/            NestJS-бэкенд
  web/            React-фронтенд (Vite)
packages/
  db/             Prisma-схема — источник истины домена
  api-schemas/     Zod-контракты, общие для FE/BE
  config/         Валидация env через Zod
  ui/             shadcn-based дизайн-система
  ai/             Промпты / RAG / провайдер-адаптеры
  eslint-config/
  typescript-config/
docs/
  decisions.md    Принципы P1-P4 и архитектурные решения ("почему так")
  specs/          Реализационные спеки фич
```

Источники истины: доменная модель — `packages/db/prisma/schema.prisma`, контракты API — `packages/api-schemas`, обоснования решений — `docs/decisions.md`.

## Архитектурные принципы

- **Стабильные ссылки** — связи по `id`/`key`, никогда по имени или локализованной строке.
- **Пережить источник** — что должно пережить изменение источника, хранит снапшот, а не живую ссылку.
- **Минимальный payload** — снапшоты и события хранят только необходимое, без дублирования тяжёлого контента.
- **Событие атомарно с мутацией** — запись в лог активности — в той же транзакции, что и сама мутация; побочные эффекты (email, embeddings) — после коммита, через очередь.
- **Тенантность как security-граница** — каждая запись скоупится по `orgId` на уровне data-access слоя (жёсткий SQL-фильтр), не на уровне доверия клиенту или модели. То же самое действует и для RAG-retrieval: организация и проект фильтруются в SQL до того, как данные попадут в промпт LLM.

## Как поднять локально

```bash
docker compose -f docker-compose.dev.yml up -d   # postgres (+pgvector) · redis · minio
pnpm install
pnpm --filter @helix/db exec prisma migrate dev  # применить миграции
pnpm --filter @helix/db exec prisma generate      # сгенерировать Prisma Client
pnpm dev                                          # все dev-серверы (turbo)
```

| Сервис | Порт |
| --- | --- |
| API | `3000` |
| Web | `5173` |
| Postgres (dev) | `5433` |
| Redis | `6379` |
| MinIO | `9000` / `9001` |
| Postgres (тесты) | `5434` |
| Prisma Studio | `5555` |

Переменные окружения — `apps/api/.env` (`DATABASE_URL`, `REDIS_URL`, JWT-секреты, S3), валидируются через `packages/config` на старте приложения.

### Демо-доступы

`pnpm db:seed` создаёт одну организацию с пятью пользователями (по одному на каждую роль RBAC) и демо-воркспейсом с проектами по канбан-фазам — для ручного тестирования матрицы прав без API-клиента.

| Email | Пароль | Роль |
| --- | --- | --- |
| `owner@helix.dev` | `helix-demo-2026` | OWNER |
| `admin@helix.dev` | `helix-demo-2026` | ADMIN |
| `manager@helix.dev` | `helix-demo-2026` | MANAGER |
| `member@helix.dev` | `helix-demo-2026` | MEMBER |
| `viewer@helix.dev` | `helix-demo-2026` | VIEWER |

## Основные команды

| Команда | Назначение |
| --- | --- |
| `pnpm build` | Собрать весь монорепозиторий (библиотеки → приложения) |
| `pnpm typecheck` | Проверка типов по всем пакетам (обязательно отдельно от тестов — vitest их не проверяет) |
| `pnpm lint` | ESLint по всем пакетам |
| `pnpm test` | Тесты (`apps/api`, требует тестовую БД на порту 5434) |
| `pnpm dev` | Все dev-серверы параллельно |
| `pnpm db:migrate` | Создать и применить Prisma-миграцию |
| `pnpm db:seed` | Наполнить БД демо-данными |
| `pnpm infra:up` / `pnpm infra:down` | Поднять/остановить Postgres, Redis, MinIO в Docker |

Перед коммитом: `pnpm typecheck && pnpm lint && pnpm test && pnpm build`.

## Вехи разработки (M0–M6)

Продукт строится по вехам: базовая доменная модель и авторизация (M0), фронтенд-MVP (M1), уведомления (M2), страницы/файлы/полнотекстовый поиск (M3), AI-чат и RAG (M4), дальше — расширение AI-возможностей и вебхуки (M5-M6). Полное описание требований — в `docs/`.
