# frontend-architecture.md — Helix (apps/web)

> **Статус:** финальный (слои 0–4). Покрывает: скелет · модель состояния · роутер · карту URL
> (слой 0) · контракт с бэком (слой 1) · kanban (слой 2, узел 1) · auth-фронт (слой 3) · стиль/
> a11y/microactions/перф (слой 4). Не спроектирован остаток слоя 2 (формы из `FieldDefinition`,
> project shell, dedup) — см. §12.
> **Тип:** спека для Claude Code. Читать вместе с `CLAUDE.md`, `docs/decisions.md`,
> `packages/api-schemas`, `docs/specs/{auth,projects,workspaces-phases}.md`. Расхождение — флагни,
> не меняй сам.

Вся спека — раскрытие лестницы ответственности в четыре строки:

```
URL      — что открыто
Query    — что известно
Feature  — что делает пользователь / какой это класс ошибки
Boundary — только если сломалась сама программа
```

Первые три — P0-FE (§0). Четвёртая — граница ошибок (§11). Если при реализации возникает вопрос
«куда положить X / где живёт Y» — ответ выводится из инвариантов ниже (сводка §8), не принимается
заново.

## 0. Корневой инвариант (P0-FE)

> **URL определяет «что открыто». Query определяет «что известно». Feature определяет
> «что делает пользователь». JWT определяет «в каком контексте». Эти ответственности
> никогда не пересекаются.**

Любое будущее решение о размещении состояния решается вопросом: _X — это открыто, известно,
делается или контекст?_ Из P0-FE механически следуют модель состояния (§4), карта URL (§6) и
модель ошибок (§7).

Производный инвариант (URL):

> **URL никогда не дублирует данные, однозначно определяемые из доверенного источника.**
> Доверенный = система знает независимо от URL и нельзя подделать навигацией (JWT, данные в
> БД). localStorage-хинт для редиректа — **не** доверенный, потому в path как контекст не идёт.

Следствия: нет `/workspaces/:wsId/projects/:projectId` (Project знает свой workspace через
`phaseId→workspaceId`); нет `/settings/:orgId` (JWT знает `activeOrgId`); есть `/contacts/:id`
(контакт не выводится ни из чего → `:id` законен).

## 1. Baseline и стек

### 1.1 React 19 + React Compiler — включён с первого дня

React Compiler 1.0 стабилен, production-ready, официальная интеграция с Vite. Включаем.

- **`useMemo`/`useCallback` в новом коде — code smell.** Компилятор мемоизирует по data-flow
  анализу на этапе сборки. Ручная мемоизация только маскировала бы нарушения Rules of React.
- Цена: код обязан быть compiler-safe (чистые компоненты, без мутации пропсов). Энфорсит
  `eslint-plugin-react-hooks` (recommended-latest preset).

### 1.2 Стек

Зафиксированный (`CLAUDE.md`, PRD §12.3): Vite + React, **TanStack Router** (см. §5, отклонение
от пина), TanStack Query, Zustand, Tailwind + shadcn/ui (из `packages/ui`), dnd-kit, TipTap.

Добавляем точечно — каждое под конкретную сущность, не «на будущее»:

| Библиотека                            | Под что                             | Почему                                           |
| ------------------------------------- | ----------------------------------- | ------------------------------------------------ |
| react-hook-form + @hookform/resolvers | формы, data-driven кастомные поля   | uncontrolled → минимум ре-рендеров; Zod-resolver |
| TanStack Table (headless)             | table view доски (FR-PRJ-7)         | headless → стилизуем своим `packages/ui`         |
| sonner                                | тосты                               | основа microactions-фидбека                      |
| cmdk                                  | command palette (⌘K)                | ложится на FR-SEARCH                             |
| Motion (ex-Framer)                    | осмысленные переходы (move, drawer) | не декор                                         |

**Не берём:** Redux (server→Query, остальное→Zustand); axios (нативный fetch + тонкая обёртка);
**i18n-библиотеку** (react-i18next и т.п.); `nuqs` (search-params нативны в TanStack Router).

**i18n — два in-house механизма, без библиотеки (уточнение).** Ранее §1.2 говорила «localize() +
jsonb покрывает P1» — но это только **доменные данные** (`LocalizedName`: имена фаз и т.п.).
**UI-микрокопию** (кнопки, лейблы, ошибки формы) `localize()` не покрывает. Поэтому:
- **Доменные строки** → `localize(value, locale)` (§6.5), источник — jsonb `{uz,ru,en}`.
- **UI-микрокопия** → `shared/i18n`: типизированные каталоги по локали + `t()`/`useT()` +
  locale-store (Zustand+persist) + zod error-map (локализация валидации). Ключи типобезопасны
  (канон ru задаёт множество, en/uz обязаны его повторить), fallback на дефолтную локаль.
- Обе системы читают **одну** локаль (locale-store) — симметрия, не дублирование. i18n-библиотеку
  не берём осознанно: плюрализация/ленивые каталоги пока не нужны; введём, когда появится триггер.

## 2. Скелет архитектуры

Feature-oriented, растущий по факту сущностей. **Anti-speculative** (`CLAUDE.md`): слой/абстракцию
заводим, когда появилась реальная сущность, не раньше. Не полный FSD — без слоёв «про запас».

```
apps/web/src/
  app/                # композиция приложения (НЕ бизнес-логика)
    router.tsx        # дерево роутов
    providers.tsx     # QueryClient, тема, ability-провайдер
    app-shell.tsx     # nav + org switcher + <Outlet/>
  features/           # ЗАВОДИМ ФИЧУ, КОГДА ОНА ЕСТЬ
    board/  project/  contacts/  workspaces/  auth/
  shared/             # переиспользуемое ВНУТРИ web, НЕ дизайн-примитивы
    api/              # fetch-клиент, query-key factory, error-нормализация
    lib/              # localize(), formatters, общие хуки
    auth/             # ability (CASL), session-хуки
  routes/             # тонкие роут-компоненты (file-based, см. §5)
```

Правила скелета:

1. **`features/*` не импортируют друг друга напрямую.** Пересечение → в `shared/` или композиция
   на уровне `routes/`.
2. **UI-примитивы только в `packages/ui`.** `apps/web/shared` — app-специфичный клей (fetch,
   localize, ability), не примитивы. Button/Dialog/Card → `packages/ui`; `useProjectMove` →
   `features/board`.
3. **`routes/` тонкие** — как контроллеры в Nest: собирают feature + запускают загрузку, ноль
   бизнес-логики.
4. **Не заводим слой до появления сущности.** Нет `entities/` про запас.

Симметрия с бэком: `routes ≈ controller`, `features ≈ service`, `shared/api ≈ repository`,
`packages/ui ≈ инфраструктурные примитивы`.

## 3. Модель владения состоянием

Четыре владельца, непересекающихся. Прямое следствие P0-FE.

```
SERVER STATE  → TanStack Query
  всё из API. Единственный владелец серверных данных. В Zustand НЕ дублируется.
URL STATE     → TanStack Router (типизированные search-params, Zod на роуте)
  фильтры доски, активный таб, пагинация. Всё, что переживает reload и шарится ссылкой.
UI STATE      → Zustand
  эфемерное: sidebar open, drag-in-progress, черновик command palette. Не переживает reload.
FORM STATE    → React Hook Form (+ Zod resolver)
  пока форма открыта. На submit → уходит в мутацию Query. Форма НЕ хранит серверную истину
  после сохранения.
```

**Инвариант:** сервер-данные никогда не копируются в Zustand. Компонент читает лид из Query по
ключу, не из глобального стора. Zustand держит только то, у чего нет серверного первоисточника.

**Единственное легитимное persisted-UI:** «последний **открытый** workspace» в localStorage —
это user-preference (не серверная истина), используется только для редиректа `/` (§6).

## 4. Роутер — TanStack Router

### ADR-FE-1. TanStack Router вместо зафиксированного React Router

Отклонение от пина (`CLAUDE.md`, PRD §12.3). Причина: client-heavy SPA-дашборд; типизированные
search-params под фильтры доски (которые держим в URL); общий кэш и паттерн мутаций с уже
выбранным TanStack Query; end-to-end типобезопасность путей/params без codegen. Цена: экосистема
меньше React Router, расхождение с PRD-стеком. **Принято.**
(React Router v7 раскрывает типобезопасность только в framework-mode/SSR; Helix — SPA, деплой
статикой на CDN, SSR нет → в library-mode остались бы с ручным приведением search-params.)

### 4.1 File-based роуты

Роуты генерятся из файлов под `routes/`. Даёт типизированное дерево и **автоматический
code-split по роуту** (работает на NFR «<1.5s на доске»: `/login` не тянет dnd-kit/Motion;
kanban-чанк грузится только на `/board`).

### 4.2 Loader = прогрев кэша, не второй источник данных

```
loader: ({ context }) => context.queryClient.ensureQueryData(...)   // греет кэш при навигации
component: useSuspenseQuery(...)                                     // читает из того же кэша
```

Единственный владелец серверных данных остаётся Query. Loader только предзагружает (убивает
водопады, включает prefetch-on-hover). **Права loader'а строго:**

> params · redirect/notFound · `ensureQueryData` (**один или несколько вызовов, но
> параллельно — `Promise.all`**) · больше ничего.

Как только в loader появляется `.map` / `localize` / вычисление permissions / merge — он перешёл
границу и стал вторым сервисным слоем. Запрещено.

### 4.3 Pathless-группировка

Группировать папкой можно **только** по guard/layout (pathless `_prefix`, не даёт URL-сегмента)
или когда сегмент реально есть в URL. Ради «просто сложить файлы рядом» — нельзя (структура
начнёт врать про навигацию). Реальная бизнес-структура живёт в `features/`, не в `routes/`.

> **URL — публичный контракт.** Переименование папки в `routes/` = смена URL = смена контракта.
> Сначала проектируется URL, потом создаётся папка.

## 5. Карта URL (финальная)

```
/login · /register                    (вне guard)
/_authenticated                       (pathless: guard + app-shell)
  /                    → redirect на lastOpenedWorkspace (localStorage-хинт)
  /workspaces          → список
  /workspaces/:id      → redirect /board
    /board             ?view ?sort (клиент-представление) · ?limitPerPhase (сервер)
    /table             (те же search-params)
                       ⚠ ?phase ?assignee ?q — СЕРВЕР ИХ ПОКА НЕ ПОДДЕРЖИВАЕТ (§6.3, зависимость)
    /settings          → redirect /phases
      /phases          dnd-reorder + БАТЧ-мутация (deferred UNIQUE!) — НЕ форма (§5.1)
      /fields          custom fields CRUD
  /projects/:id        → redirect /overview   (плоско: проект знает workspace)
    /overview  /contacts  /tasks  /activity
  /contacts · /contacts/:id           (org-scoped, не выводится → :id законен)
  /settings            → redirect /org        (без :orgId — берётся из JWT)
    /org  /members  /api-keys  /webhooks      (часть — M5)
```

Правила карты:

- **path идентифицирует ресурс · search идентифицирует представление ресурса.**
- **search-params:** Zod-схема с `.catch(дефолт)` (не `.default()`) — устойчивы к мусору в URL.
  Битый param из старой ссылки мягко падает в дефолт, не роняет роут в error-boundary.
  «Голый» `/board` и `/board?view=kanban` нормализуются в один стейт.
- Workspace — корень агрегата: board/table/settings — представления одного агрегата (вложены).
- Project — плоско (`/projects/:id`): проект знает свой workspace, URL это не дублирует.
- Contacts — не вкладываем: org-scoped, а не project-scoped.

### 5.1 `/settings/phases` — не форма, а второй dnd-экран

Фазы редактируются drag-to-reorder (FR-WS-2) поверх жёсткого бэкового инварианта
`Phase(workspaceId, order)` UNIQUE **DEFERRABLE**. Reorder-мутация обязана слать **весь
перестроенный порядок разом** (одна транзакция, deferred constraint проверяется на коммите).
N патчей по одному нарушат UNIQUE до дефера. → страница наследует kanban-паттерн (dnd-kit +
оптимистичный reorder + батч-мутация), не паттерн формы.

### 5.2 Смена организации — действие, не URL

Org — контекст (JWT), не ресурс в URL. Переключение = смена контекста, не навигация:

```
Org Switcher
  ↓ POST /v1/auth/switch-org              → новый access в ТЕЛЕ ответа (AuthResult), activeOrgId=B
  ↓ сохранить access в память JS          (access НЕ в cookie; см. модель токенов ниже)
  ↓ queryClient.clear()                   → СНОСИМ кэш (НЕ invalidate — там тенант A!)
  ↓ navigate("/workspaces")               → чистый старт, loader греет кэш заново
```

`clear()`, не `invalidate`: `invalidate` на миг оставил бы в UI данные оргиA, пока грузится
оргаB — межтенантная утечка на уровне кэша. Это фронтовое зеркало бэкового tenant-инварианта
(composite-FK backbone в БД ↔ `clear()` в кэше).

**Модель токенов на клиенте (из `auth.md` §1, §4 — фиксируем, детали silent-refresh → слой 3):**
access-токен приходит в **теле** ответа (`login`/`register`/`refresh`/`switch-org` → `AuthResult
{ accessToken, user }`) и живёт в **памяти JS** (переменная/React state, НЕ localStorage, НЕ
cookie — при XSS утечёт максимум 15-мин токен). refresh-токен — в **httpOnly+SameSite=Lax+Secure
cookie**, JS его не читает. Эндпоинты: `/v1/auth/{register,login,refresh,logout,logout-all,
switch-org,me}`. Access в памяти — это session-state, не server-state Query и не UI-state Zustand;
владелец — auth-провайдер (слой 3).

## 6. Контракт с бэком (слой 1)

### 6.1 Четыре языка, четыре границы

```
api-schemas (Zod)   ЯЗЫК СЕТИ. Единственный источник контрактных типов FE.
      ↓ request({ schema })  — parse ПО УМОЛЧАНИЮ (граница доверия = сеть)
      ↓
TanStack Query      ГРАНИЦА ДОВЕРИЯ. До кэша недоверенно, после — гарантированно по контракту.
      ↓ select (ЧИСТЫЙ: без локали/времени/browser API; меняет ФОРМУ)
      ↓
ViewModel           ЯЗЫК ПРИЛОЖЕНИЯ. Уже не сеть, ещё не показ.
      ↓ render + useLocalize()/Intl (меняет ПРЕДСТАВЛЕНИЕ, локале-зависимо)
      ↓
UI                  ЯЗЫК ПОКАЗА. НЕ импортирует *Response. НЕ знает про envelope.
```

### 6.2 Runtime-валидация ответа — по умолчанию, отключение по endpoint'у

Граница доверия проходит через сеть: бэк валидирует Zod на выходе, фронт получает по HTTP (сеть,
версии, сериализация могут разъехаться; `z.infer` этого не видит). Значит parse на входе фронта:

- **`request({ schema })` парсит `*ResponseSchema` по умолчанию.** До Query недоверенно, после —
  по контракту. Симметрия с бэковым Zod-пайпом на входе контроллера.
- **Отключение — свойство endpoint'а, не окружения.** `request({ schema, validate: false })` —
  осознанно, по конкретному эндпоинту. **Не** «dev vs prod» (это дало бы дивергенцию поведения
  между окружениями — худший класс багов). Даже при `validate: false` тип отдаётся через
  `z.infer<typeof Schema>`, **не `any`** (отключаем рантайм-проверку, не типовой контракт).
- **Отключаем только после профайлера.** «Все API проходят runtime-валидацию; исключение — если
  профилирование доказало, что parse стал bottleneck», не наоборот. Настоящий bottleneck доски —
  виртуализация × dnd × reconciliation, не parse 20 воркспейсов.
- На будущее (не сейчас): `safeParse` для graceful-degrade на тяжёлом эндпоинте — третья точка
  между «parse и падаем» и «не parse вообще».

### 6.3 Query-key factory

> **queryKey описывает запрос к серверу, а не состояние UI.** queryKey = ровно то, что влияет на
> ответ сервера. Не больше (иначе дубли кэша), не меньше (иначе stale под новым фильтром).

- Серверные параметры, которые **реально существуют в API сегодня** → **входят** в ключ:
  - board-эндпоинт: `?limitPerPhase` (`BoardQuerySchema`).
  - column-эндпоинт (подгрузка колонки, keyset): `?cursorRank ?cursorId ?limit` (`ColumnQuerySchema`).
  - board и column — **разные запросы → разные ключи** (`queryKeys.board(wsId)` vs
    `queryKeys.column(phaseId, cursor)`).
- Клиентские представления (`?sort ?view` — живут в `select`/render) → **не входят**.
- ⚠ **`?phase ?assignee ?q` сервер НЕ поддерживает** (в `BoardQuerySchema` только `limitPerPhase`).
  До появления серверной фильтрации: либо клиентский фильтр (тогда **не в ключе**, живёт в
  `select`/render), либо фича отложена до вехи (`assignee` → visibility M6, `q` → search M5,
  `phase`-фильтр — когда появится server-side). **Не** класть их в ключ как «серверные», пока SQL
  их не принимает — иначе ключ врёт про запрос (нарушение KEY-1).
- **`activeOrgId` — корень каждого ключа:** `['org', orgId, 'workspace', wsId, 'board', { limitPerPhase }]`.
  При `visibility=ASSIGNED` сервер возвращает разное разным юзерам на тот же URL → ответ зависит
  от JWT; orgId в корне ключа делает межтенантную коллизию по ключу невозможной (defense-in-depth,
  зеркало composite-FK; `clear()` при свитче остаётся для памяти и чистоты UI).
- **Централизованная фабрика** `queryKeys.*`, не ручные массивы по проекту (ручные = рассинхрон
  ключей = тихие промахи кэша). Закрытое множество ключей под контролем одного места — тот же
  паттерн, что `ActivityRecorder.record()` на бэке.
- Иерархические префиксы → веерная инвалидация: `invalidateQueries({ queryKey: queryKeys.workspace(wsId) })`
  сносит всё под воркспейсом одним вызовом.

### 6.4 Ошибки — Transport (shared) vs Domain (feature)

> **shared знает только HTTP и JSON. Feature знает бизнес.**

`shared/api` не знает `Phase`/`Workspace`/`Lead` и не знает доменных кодов
(`WORKSPACE_VERSION_CONFLICT`, `PHASE_NOT_EMPTY` — оба 409, но это язык домена). Иначе `shared`
обрастает бизнесом и перестаёт быть shared.

```
shared/api:      TransportError = Network | Unauthorized | Forbidden
                                | Validation | Conflict | Unexpected     (только HTTP)
                       ↓  feature интерпретирует code внутри статуса:
features/board:  BoardError = WorkspaceConflict | PhaseNotEmpty | PermissionDenied
```

`TransportError` типизирован по HTTP-статусу, но **несёт непрозрачный payload** (`error.code`,
`error.details` из envelope) — читает только тот, кто знает язык домена. Транспорт переносит,
не интерпретирует (конверт: почта знает адрес, не содержание). Маппинг HTTP→domain живёт в
feature, не в fetch-клиенте.

Бэковый exception filter уже отдаёт доменные ошибки осмысленным HTTP (409 на optimistic-lock/FK,
не 500) — фронту есть что интерпретировать.

### 6.5 ViewModel

`select` — граница языков: вход = язык сети (DTO), выход = язык приложения. UI **не импортирует
`*Response`** (иначе знает про envelope/`LocalizedName`/форму сети, и сетевой рефактор ломает UI).

Разрешение противоречия с «localize в render»: `select` чист и **не знает локали** (иначе кэш
фрагментируется по языкам). Значит ViewModel меняет **форму** (плоскую, под нужды компонента), но
локале-зависимые поля оставляет **сырыми** до render.

Важно про типы Helix (из кода): **`Project.title` — простая строка**, НЕ локализована
(`CreateProjectSchema { title: string }`, `ProjectResponseSchema.title`). Локализовано только
`Phase.name` — тип `LocalizedName` = jsonb `{uz?, ru?, en?}`, рендерится через
`localize(value, locale)` (`api-schemas/common.ts`). Пример карточки лида:

```
DTO:        { title: string, phase: { name: LocalizedName, color }, value, currency, rank }
   ↓ select (чистый, меняет ФОРМУ):
ViewModel:  { title: string, phaseName: LocalizedName, phaseColor, amount:{value,currency}, rank }
   ↓ render: title как есть · localize(phaseName) · Intl(amount)  (локале-зависимо):
UI:         title="Сделка с Acme"   phase="Discovery"/"Обсуждение"   amount="$12 000"
```

`title` проходит насквозь строкой (нечего локализовать). `phaseName` остаётся `LocalizedName` в
кэше и ViewModel, локализуется только на render — переключение языка = ре-рендер, ноль рефетчей.

Правило: **`select` меняет форму (чисто, кэшируемо) · render меняет представление (локаль/Intl).**
Локале-зависимые поля (`LocalizedName`, `value+currency`, даты) остаются сырыми до render.

## 7. Kanban (слой 2, узел 1)

### ADR-FE-2. Kanban: порядок в модели, не в DOM

> **DOM показывает порядок. `rank` определяет порядок.** DOM никогда не источник истины для
> сортировки.

DOM даёт ровно один бит — намерение («курсор над картой X»). Всё остальное — на сервере.

**Контракт move — по соседям-id, ранг считает ТОЛЬКО сервер (из `projects.md` §4.1):**

```
POST /v1/projects/:id/move  { toPhaseId, afterId?, beforeId? }   ← соседи по ID
```

Бэк **сознательно отверг** `{ rank }` (клиент считает сам) — «алгоритм утекает во фронт, две
реализации синхронно», и `{ index }` — нестабильная позиция (P1). Контракт по id — ещё и
**необходимое условие безопасной рекомпакции** (§ниже): рекомпакция инвалидирует ранги, но не id.
→ **клиент НЕ считает rank и НЕ хранит fractional-алгоритм.** rank целиком server-owned.

Отсюда форма оптимистичного апдейта — **сплайс массива по позиции дропа, без вычисления ранга:**

```
DOM: "курсор между картами A и B" (намерение)
  → мутация: { toPhaseId, afterId: A.id, beforeId: B.id }
  → optimistic: splice карту в кэш-массив на позицию между A и B (порядок массива, БЕЗ rank)
  → сервер считает реальный rank (generateKeyBetween) + status(phase.type), возвращает проект
  → onSuccess: пропатчить rank+status карты из ответа
```

**Клиент рендерит колонку по ПОРЯДКУ МАССИВА** (сервер отдал `ORDER BY rank, id`; клиент его
сохраняет), а **не пере-сортирует по rank на каждый рендер.** Это ключ: клиенту rank почти не
нужен — только как непрозрачный keyset-курсор (`?cursorRank ?cursorId`) для подгрузки колонки.
Пере-сортировка по rank на клиенте была бы ошибкой (см. рекомпакцию).

Виртуализация (рендерить ли узлы) и источник порядка (сервер/rank) — **ортогональные оси**.
Инвариант «порядок в модели» верен всегда, независимо от виртуализации.

**M1:**

- виртуализации нет — **профилирование не показало необходимости** (не «не нужна»: утверждение о
  перфе фальсифицируемо, контролируется измерением, не предположением).
- drag = обычный список; штатный dnd-kit collision detection.
- move = optimistic:
  ```
  onMutate:  cancelQueries(board); snapshot = getQueryData(board);
             setQueryData(board, splice карту по позиции); return { snapshot }
  onError:   setQueryData(board, snapshot)         // откат к снимку, НЕ рефетч
             (409 STALE_NEIGHBORS → это тот же откат + рефетч колонки, см. §6.4)
  onSuccess: patch rank+status карты ИЗ ОТВЕТА    // НЕ «ничего»: реальный rank только у сервера
  onSettled: (M1 — пусто; см. рекомпакцию и §9)
  ```
  invalidate — **не** механизм синхронизации move (порядок массива уже верен; сервер лишь
  доставляет реальный rank двинутой карты).
- **Рекомпакция фазы (`projects.md` §4.4):** при `len(rank) > 32` сервер перенумеровывает **всю
  фазу** в той же транзакции — ранги ДРУГИХ карт меняются, но **порядок и id сохраняются**, а
  ответ move содержит только одну карту. Последствие для кэша:
  - **карты НЕ прыгают** — клиент рендерит по порядку массива (не по rank), а порядок+id целы.
    Именно поэтому «не пере-сортировать по rank на клиенте» — не стиль, а корректность.
  - остаточная стейл-ность: `rank`-строки других карт в кэше устаревают. Клиент использует их
    только как keyset-курсор → при активном infinite-scroll рекомпактнутой колонки следующая
    страница может съехать. Edge-case. Прикрытие: рефетч колонки после move, который клиент не
    может распознать как рекомпактнувший (сервер move-ответом это не сигналит в M1), ИЛИ
    `onSettled: invalidate(колонка)` когда он появится (отложено, §9). В M1 — принять как редкий
    край; полноценно закроется с realtime (M6).
- **board не трогает DOM-измерения напрямую** — это **дисциплина границы, НЕ интерфейс.**
  Anti-speculative: `BoardViewport`-адаптер под виртуализацию не заводим сейчас (спекулятивная
  абстракция под несуществующую 2-ю реализацию). Точка замены — один локальный `<CardList>`;
  интерфейс извлекаем из двух реальных реализаций, когда придёт виртуализация. Инвариант «порядок
  в модели» уже делает переход дешёвым бесплатно.

**Триггер виртуализации** (измеримый, не «500 карт»): `p95 drag frame > 16ms` (бюджет кадра
60fps) **ИЛИ** одна фаза > 200 карт → тогда виртуализация + **data-driven collision** (цель дропа
вычисляется по rank-порядку, не по DOM-узлу, которого может не быть во вьюпорте).

**Отвергнуто:** виртуализация с переключением DOM-режима на время drag — перестройка дерева в
момент начала взаимодействия = баги + скачок перфа в худшей точке.

## 8. Auth-фронт (слой 3)

### ADR-FE-4 (P0-AUTH-FE) — корневой инвариант слоя

> **Любое изменение идентичности пользователя полностью инвалидирует клиентский контекст
> безопасности.** Идентичность меняют: logout · refresh failure · switch-org · смена роли (после
> рефетча `me`) · истечение сессии. Следствия единые для всех пяти: `cancelQueries()` →
> `queryClient.clear()` → сброс ability → сброс user-завязанного UI-state (Zustand) → redirect
> `/login` **или** prefetch нового контекста.

Это объясняет, почему `queryClient.clear()` встречается в трёх местах (switch-org §5.2, hard
logout §8.1, failed refresh §8.1) — не три совпадения, а один инвариант в трёх проявлениях.

### 8.1 Silent refresh на 401 — single-flight (протокол, не оптимизация)

Access ~15 мин в памяти JS, refresh в httpOnly cookie. Access протух → 401 → прозрачно обновить
и повторить. **Мина (связка с `auth.md` §5):** на доске летят ~10 запросов; access протух → все
получают 401 → наивно каждый дёргает `/refresh`. Но refresh **ротируется**: первый обновит
цепочку, остальные 9 придут с потраченным refresh → сигнал `REUSE` → бэк **убивает семью** →
пользователь разлогинен на легитимном истечении. Значит:

> **Инвариант: одна refresh-cookie → ровно один одновременно выполняющийся refresh-запрос.**
> Фронтовое зеркало бэкового «refresh используется ровно один раз». Single-flight — **условие
> совместимости с reuse-detection**, не удобство.

**Проактивный lock (не только retry, но и на новые запросы):**

```
любой исходящий запрос:
  if (refreshPromise != null) await refreshPromise     // сначала дождись идущего refresh
  access = readFromMemory()                            // ТОЛЬКО потом читай access
  send(access)
первый 401 → берёт lock → один POST /v1/auth/refresh; остальные ждут refreshPromise
refresh OK   → новый access в память → все ждавшие повторяются с новым access
refresh FAIL → hard logout (P0-AUTH-FE)
```

Проактивность закрывает вторую гонку: запрос, стартующий во время refresh, не улетит со старым
access (иначе лишний 401 → лишний риск задеть reuse-detection).

**Живёт в fetch-клиенте (`shared/api`)** — тот же choke-point, что парсит Zod (§6.2) и нормализует
ошибки (§6.4). Два обязательных исключения: сам `/refresh` не оборачивается в 401-retry (иначе
цикл); `/login`/`/register` 401 — доменный «неверные креды», не «access протух», не рефрешить.

**Единственный автоматический retry во всём fetch-клиенте — post-refresh replay.** Никаких
`retry(3)` на 401, никаких «повторим ещё раз» — любой незапланированный повтор рискует послать
второй запрос с потраченным токеном.

**Hard logout / failed refresh** (P0-AUTH-FE): все pending завершаются как **`SessionExpired`** —
отдельный терминальный исход, не `401`/`Cancelled`/`Network`/`Forbidden`. UI по нему не показывает
ошибку, только переход:

```
refresh failed → invalidate session → cancelQueries() → queryClient.clear() → navigate(/login)
```

### 8.2 Permission-aware rendering — capabilities с сервера, UI косметичен

> **⚠ Статус контракта (сверено с кодом).** Серверный RBAC-энфорсмент (CASL) в M1 **реализован**:
> `apps/api/src/core/authz` — `defineAbilityForRole()` (матрица PRD Appendix B) + `PoliciesGuard` /
> `@CheckPolicy` на каждом мутирующем эндпоинте. Отсутствует только **FE-проекция** `capabilities`:
> сегодня `currentUserSchema` = `{id, email, name, activeOrgId, role}`, поля `capabilities` не
> содержит. Оно **строится в M1** (веха H плана фронта) как тонкая сериализация уже существующего
> ability — НЕ отдельная веха и НЕ `packRules`. До этого шага permission-aware rendering не работает,
> но серверный guard — единственный энфорсер в любом случае (§8.2.1), поэтому косметика кнопок на
> безопасность не влияет.

`CLAUDE.md`: UI-скрытие косметическое, enforcement на сервере. Фронт **не переопределяет правила
у себя** (два набора синхронно = дрейф матрицы прав Appendix B). Но и **не получает `packRules`**
(сериализованные правила CASL связали бы фронт с внутренним языком бэковой authz — то же, против
чего §6.4/§6.5). Контракт: бэк отдаёт **capabilities**, плоский JSON возможностей, не правил:

```json
{ "workspace": { "manage": true }, "project": { "create": true, "edit": true, "move": true } }
```

Бэк решает _как_ их вычислить (CASL/RLS/что угодно), фронт — _как_ применить (спрятать кнопку).
CASL может исчезнуть — контракт не изменится. Приходят с `me` (расширение `currentUserSchema` в
M1), scoped по `activeOrgId`, **не кэшируются дольше ability-контекста** (сбрасываются
P0-AUTH-FE). Прямое следствие «role не в JWT, читается свежей» (`auth.md`): права — тоже свежие,
не захардкожены во фронт.

Три инварианта (#### 8.2.1; #2/403 действует уже сейчас, #1 косметика — с проекцией capabilities):

1. **FE-capability = «показывать ли кнопку», сервер = «сработает ли действие».** Скрытая кнопка —
   не безопасность; каждое действие проходит серверный policy-guard.
2. **403 — нормальный доменный исход, не баг.** FE-capability разошлась с сервером (гонка,
   реассайн между рендером и кликом) → сервер вернёт 403 → `TransportError.Forbidden →
BoardError.PermissionDenied` (§6.4) → тост + **рефетч capabilities**. FE-права оптимистичны,
   сервер — истина.

### ADR-FE-3. Action authorization ≠ Data visibility

> `ability.can('edit', project)` **никогда** не отвечает на «вижу ли я project». Видимость —
> data-scope: сервер фильтрует, какие лиды вообще вернутся (§6.3, `visibility=ASSIGNED`). Невидимый
> лид физически отсутствует в ответе. FE-capability работает **только над тем, что уже пришло**
> (action-level), не решает видимость (data-level). Путаница этих двух — классический источник дыр.

**M1-край:** без realtime (M6) реассайн даёт стейл — отобранный лид висит в кэше доски до рефетча
`me` (по навигации/фокусу окна/инвалидации, не мгновенно). Принимаем; закрывается с WS — тот же
задел, что рекомпакция (§7).

### 8.3 App shell + org switcher

- Shell оборачивает `_authenticated` (pathless, §4.3), **persistent layout route** — не
  ремоунтится на навигации (переход board→project→назад не пересобирает nav, не теряет скролл).
- **Не группировать данные с разной частотой инвалидации.** M1-loader `_authenticated` грузит
  `me` (контекст идентичности, редкий). `workspaces` (частый, может быть большим списком у Member)
  → **отдельный Query** (своя инвалидация; создание воркспейса не трогает `me`). То же правило, что
  «данные, обновляемые вместе, живут вместе» (§6.3). `capabilities` войдут в `me` в M1 (§8.2, веха
  H); `organizations` — с инвайтами (ниже), их в M1-loader нет.
- **⚠ Имя активной орги (M1-потребность, отдельная от switcher).** Shell показывает контекст —
  имя текущей орги в панели. Но `me` отдаёт `activeOrgId` (только id), а `currentUserSchema.name` —
  имя **юзера**, не орги. Значит нужен источник имени активной орги: минимальное расширение `me` до
  `activeOrg: {id, name}` **или** отдельный org-запрос. Это **не** список `organizations` — решается
  при постройке shell, малой ценой. Не откладывать вместе со switcher.
- **⚠ Org switcher — форвард-зависимость (defer до инвайтов).** В M1 регистрация даёт личную оргу,
  инвайтов нет (`auth.md` §9.1) → юзер в **одной** орге → switcher переключать нечего. Список
  `organizations: [{id, name, role}]` в `me` тривиален (длины 1) до инвайтов — расширять контракт
  сейчас = строить его раньше и потребителя, и multi-org фичи, что даёт данным смысл. Строится
  **вместе с инвайтами/multi-org**. Целевой UI (когда появится): список орг из `me`, флоу §5.2 с
  prefetch (`switch → clear → prefetch board нового ws с новым access → navigate`, best-effort).

## 9. Стиль, microactions, a11y, перф (слой 4)

### 9.1 A11y — keyboard-navigable kanban (WCAG 2.1 AA, требование NFR)

Клавиатурный drag — **дискретные шаги** (`Space` взять → стрелки шаг → `Space`/`Esc`), не
непрерывная траектория. dnd-kit `KeyboardSensor` + `sortableKeyboardCoordinates`. Контракт move
по соседям-id (§7) окупается второй раз: клавиатурному сенсору **не нужны координаты** — стрелка =
«стать после следующей карты» = `{afterId, beforeId}` по массиву. Мышь даёт намерение пикселями,
клавиатура — индексом, **оба сходятся в один контракт move**. Считай мы rank по DOM-координатам —
клавиатурный drag пришлось бы строить отдельно.

Обязательно (a11y-контракт доски):

- `Space` взять/бросить · стрелки шаг · `Esc` отмена (возврат на исходную — см. §9.2).
- **Live region `aria-live="assertive"`** (dnd-kit `announcements`): «Карта X взята»,
  «перемещена в Discovery, 3 из 12», локализовано (`localize` на render-границе).
- **Focus management:** после дропа и патча из ответа (§7) фокус остаётся на карте, не прыгает.
- Карта — фокусируемый элемент с ролью (`role`/`tabindex`), колонка `role="list"`. Не `<div
onClick>`.

> **Инвариант a11y:** `packages/ui` на Radix даёт клавиатуру/фокус/ARIA для примитивов бесплатно.
> Кастомный интерактив (карта, dnd) — наша ответственность: либо примитив из `ui`, либо явный ARIA-
> контракт. Не строим интерактив на голом `<div onClick>`.

**M1-честность:** клавиатурный kanban + focus + live region строим **сразу** (переделка drag-
механики постфактум дорога); полный AA-аудит (контрасты, SR end-to-end) — инкрементально.

### 9.2 Error boundaries — три класса, не смешиваются

> **Error Boundary — только для того, что разработчик не предвидел.** Все ожидаемые исходы
> (validation, forbidden, conflict, session-expired, network) обрабатываются **до** boundary. `throw`
> ожидаемой ошибки в рендере — запрещён (иначе boundary деградирует в бизнес-логику).

```
SessionExpired      → НЕ error UI; это P0-AUTH-FE-переход (уже летим на /login)
TransportError.*    → доменный исход, в feature (тост/inline), НЕ всплывает в boundary
непредвиденный throw → работа boundary: экран «сломалось» + reset
```

Уровни: **route-level** `errorComponent` (сбой одного роута не роняет persistent shell §8.3) ·
**root** (последняя сеть). Query-ошибки по умолчанию **не** в boundary — возвращаются как `isError`,
feature решает. Исключение — `useSuspenseQuery` (бросает → ловит route-boundary; для него граница
обязательна). Это UI-продолжение §6.4: boundary знает «сломалось/нет», feature знает «что за сбой».

### 9.3 Единый rollback pipeline

> Отмена drag (`Esc`, до drop) и rollback неудачной optimistic-мутации (после drop, 409) —
> **один механизм** восстановления порядка из снимка `onMutate` (§7). Визуально одинаковы,
> триггеры разные, реализация одна: `restore(snapshot)` с двумя входами. Не две системы отката.

### 9.4 Дизайн-токены и тема

Токены — CSS-переменные (`--color-* --space-* --radius-*`) в `packages/ui`, Tailwind через
`theme.extend`; shadcn/ui уже на них. Dark mode — класс `.dark` на корне, не дублирование палитр.

> **Feature-код обращается к цвету только через семантический токен** (`text-primary`, `bg-surface`)
> — никогда hex/rgb, никогда сырая Tailwind-палитра (`blue-500`) для брендовых цветов. Токен → CSS-
> переменная → тема. Редизайн меняет тему, не feature-код. (То же, что «UI не импортирует
> `*Response`»: feature говорит семантикой, не реализацией.)

**i18n/RTL-задел (NFR):** logical properties (`ms-*`/`me-*`, не `ml-*`/`mr-*`) — RTL-ready сразу.

### 9.5 Motion

> **Motion подтверждает изменение состояния, а не несёт его.** Тест: с `prefers-reduced-motion`
> (анимации off) приложение обязано остаться полностью понятным. Ломается без motion → состояние
> спрятано в анимацию = дефект. (Этот тест автоматически покрывает WCAG `prefers-reduced-motion`.)

Разрешено: карта на move, drawer/dialog вход-выход, skeleton→content. Запрещено: декор на списках,
hover-анимации на каждой из 500 карт.

### 9.6 Skeleton — против мерцания

> Skeleton появляется **только если** ожидание превысило порог (~100–200мс, число при реализации).
> Быстрый ответ рендерит контент сразу, без вспышки. Skeleton держит layout (без CLS), spinner —
> почти нигде.

Усиливает loader-prefetch (§4.2): большинство навигаций под порогом → skeleton не появляется вовсе.
Для доски — skeleton-колонки под форму реальных.

### 9.7 Перф-бюджет — измеримый

NFR: доска <1.5s на ≤500 карт. Из принятого почти бесплатно: code-split по роуту (§4.1), loader-
prefetch (нет водопадов), React Compiler (нет лишних ре-рендеров), array-order рендер без клиентской
пере-сортировки (§7).

> **Любая оптимизация — только после измеренного bottleneck** в React DevTools Profiler / browser
> Performance. Ни ручной мемоизации «на глаз» (её место занял компилятор §1.1), ни спекулятивного
> дробления. Компилятор снял мемоизацию, но не отменил дорогие вычисления (тяжёлый `select`, лишний
> рефетч). Метрики в CI: board TTI, `p95 drag frame`, bundle-size gate на роут.

**Сквозной принцип «сначала измерь»** объединяет Zod-parse (§6.2), виртуализацию (§7) и этот
бюджет — все три частные случаи одного правила.

## 11. Граница ошибок (четвёртая ступень лестницы)

Три первые ступени — P0-FE (§0). Четвёртая: **Boundary — только если сломалась сама программа.**
Полная лестница: URL (что открыто) → Query (что известно) → Feature (что делает юзер / класс
ошибки) → Boundary (непредвиденный сбой). Классы ошибок распределены по ступеням: доменные — в
feature (§6.4), `SessionExpired` — глобальный auth-переход (§8.1, минуя UI ошибок), непредвиденный
throw — boundary (§9.2). Ни один класс не смешивается с другим.

## 12. Отложенные развилки (решаются по триггеру, не сейчас)

- `onSettled: invalidate` на доске — пуст в M1, включается с realtime board (WS, PRD §12.2);
  заодно закроет остаточную стейл-ность keyset-курсора после рекомпакции фазы (§7) и стейл-реассайн
  capabilities (§8.2).
- Server-side фильтры доски `?phase ?assignee ?q` — зависят от вех API (`assignee`→visibility M6,
  `q`→search M5). До тех пор не в queryKey (§6.3). Когда появятся — входят в ключ board-запроса.
- `safeParse` graceful-degrade — вводим, если профайлер покажет parse-bottleneck (§6.2).
- Виртуализация доски — по триггеру `p95 drag frame >16ms` или `фаза >200` (§7).
- `BoardViewport`-интерфейс — извлекаем из 2-й реализации рендеринга, не раньше (§7).
- Skeleton-порог (~100–200мс) — конкретное число при реализации (§9.6).
- **`organizations: [{id,name,role}]` в `me`** — отложено до инвайтов/multi-org (§8.3): в M1 юзер
  в одной орге, список тривиален (длины 1); расширяем `currentUserSchema` вместе с инвайт-флоу.
  (`capabilities` и `activeOrg:{id,name}` — НЕ здесь: оба строятся в M1, см. §8.2 / §8.3.
  `currentUserSchema` сегодня = `{id,email,name,activeOrgId,role}`.)
