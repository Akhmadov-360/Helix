## 3. `Project.rank` — строковый fractional index

### Решение

`rank String @db.VarChar(64)`, алфавит **base62** (`0-9A-Za-z`), генерация — библиотека
`fractional-indexing`. Порядок карточек в колонке: `ORDER BY rank, id`.

### Почему не Int (как у Phase.order)

Один и тот же вопрос «как хранить порядок» получает разные ответы по **кардинальности и частоте
вставки в середину**:

|                    | Phase.order (Int + перенумерация) | Project.rank (строковый ранг) |
| ------------------ | --------------------------------- | ----------------------------- |
| Элементов          | O(10) колонок                     | сотни карточек в колонке      |
| Вставка в середину | O(n) UPDATE — дёшево              | 1 UPDATE                      |
| Уникальность       | **инвариант** (DEFERRABLE unique) | **не** инвариант (§4.2)       |
| Природа порядка    | конфигурация доски                | презентация                   |

Float/Decimal отвергнут не «на всякий случай»: `(a+b)/2` для соседних double исчерпывает мантиссу
за ~50 вставок **в одну и ту же щель**. Строка деградирует ростом длины (лечится рекомпакцией, §4.4),
а не потерей корректности.

### 3.1 Коллация — MANUAL MIGRATION POINT #4

Fractional indexing предполагает **байтовое** сравнение строк. Коллация Postgres по умолчанию — нет:

```
COLLATE "C"          :  'B' < 'a'      (66 < 97)   ← так думает алгоритм
COLLATE "en_US.UTF-8":  'a' < 'B'      (регистр вторичен)
```

При дефолтной коллации сортировка в БД разойдётся с логикой генератора → карточки поедут, причём
не всегда, а на конкретных парах ключей. Поэтому:

```sql
ALTER TABLE "Project" ALTER COLUMN "rank" TYPE varchar(64) COLLATE "C";
```

**Защита ОДИНАРНАЯ, и это принято осознанно.** Изначально планировалось две (lowercase-алфавит
`0-9a-z` + коллация), но base36-lowercase несовместим с библиотекой: в её формате знак целой части
кодируется регистром головы (`a-z` = положительная, `A-Z` = отрицательная), а отрицательная
возникает при каждой вставке **перед первым** элементом — то есть при «новые лиды сверху» (§3.3)
постоянно. Выбор был: base62 + библиотека, либо lowercase + своя реализация (~60 строк).
Выбрана библиотека → защита осталась одна: коллация. Следовательно **тест на неё несущий, а не
декоративный** (§13).

> **Механизм риска здесь ДРУГОЙ, чем у DEFERRABLE (#1).** Коллация лежит в файле миграции, shadow DB
> её воспроизводит — сам по себе drift не возникает. Риск в том, что правка типа колонки в
> `schema.prisma` (`VarChar(64)` → `VarChar(128)`) заставит Prisma выпустить `ALTER COLUMN ... TYPE`,
> который **сбрасывает коллацию молча**. Точная формулировка риска важнее, чем факт наличия пункта.

**Перед реализацией — подтвердить поведение библиотеки эмпирически, не по памяти:**

```ts
generateKeyBetween(null, null); // ожидаем "a0"
generateKeyBetween(null, "a0"); // ожидаем заглавную ("Zz") → подтверждает несовместимость base36
generateKeyBetween("a0", null); // "a1"
```

### 3.2 Индекс

```prisma
@@index([phaseId, rank, id])
```

`id` в индексе — не косметика: он делает скан **полностью упорядоченным** при tie-break (§4.2) и
служит тем же индексом для keyset-пагинации `WHERE (rank, id) > ($2, $3)` (§8). Индекс и решение о
неуникальности ранга — связанная пара, не два независимых пункта.

### 3.3 Новые лиды — наверх колонки

Продуктовое: входящий лид должен быть виден сразу. `rank = generateKeyBetween(null, firstRank)`.

## 4. Операции над рангом

### 4.1 Контракт move — соседи по **id**, не по индексу и не по рангу

```
POST /v1/projects/:id/move
{ "toPhaseId": "ph_x", "afterId": "prj_a", "beforeId": "prj_b" }
```

Отвергнуто:

- **`{ index: 3 }`** — позиция нестабильна: пока клиент думал, кто-то вставил карточку выше.
  Прямое нарушение P1 (опора на нестабильное значение).
- **`{ rank: "a3" }` (клиент считает сам)** — алгоритм утекает во фронт (две реализации синхронно),
  клиент может прислать любую строку.

**Дополнительная, не декоративная причина:** рекомпакция (§4.4) **инвалидирует ранги, но не id**.
Контракт по id — необходимое условие того, чтобы рекомпакция была безопасной. Два решения, принятые
по независимым причинам, оказались связаны — на защите приводить вместе.

Дефолт при отсутствии соседей (drag на пустую колонку / move в другую фазу без указания позиции) —
**наверх**, консистентно с созданием (§3.3).

### 4.2 Ранг НЕ уникален, tie-break по `id`

Два одновременных prepend прочитают один и тот же `firstRank` и сгенерируют одинаковый ключ. Для
публичного интейка (`POST /v1/public/leads`, M5) это не редкость, а **систематика**: все новые
карточки прицельно бьют в одну щель.

UNIQUE превратил бы безобидную гонку в отказ пользователю. Вместо этого — детерминированный
tie-break: `ORDER BY rank, id`.

> **Принято осознанно (расхождение с §3.3).** `cuid` начинается с timestamp → `id ASC` ≈ порядок
> создания. Среди столкнувшихся ранков более **старый** лид окажется выше нового, то есть обратно
> продуктовому решению «новые сверху». Расхождение живёт только внутри субсекундного окна
> одновременных вставок; за его пределами ранги различны и порядок верен. Альтернатива
> (`ORDER BY rank ASC, id DESC`) ломает симметрию keyset-курсора (условие становится
> `rank > $2 OR (rank = $2 AND id < $3)`, индекс — `(phaseId, rank, id DESC)`) — цена выше выгоды.

Та же логика, что у дедупа контактов: **дубль терпим и лечится, отказ пользователю — нет.**

### 4.3 Advisory lock — на ОБОИХ путях

```sql
SELECT pg_advisory_xact_lock(4242, hashtext($phaseId));   -- 4242 = namespace "phase-rank"
```

- **Берётся и в move, и в рекомпакции.** Лок только на рекомпакции — не взаимное исключение:
  он защитил бы её от другой рекомпакции и ни от чего больше.
- **Двухаргументная форма.** `phaseId` — cuid, `hashtext()` даёт 32 бита → коллизии между разными
  фазами реальны (не ошибка корректности, но взаимные блокировки чужих досок). Неймспейс их разводит.
- **`_xact_`, не сессионный** — освобождается на commit/rollback, забыть unlock нельзя.
- При смене фазы лок нужен на **целевую** фазу; из исходной мы только уходим.

### 4.4 Рекомпакция — амортизация, а не отдельная фича

Длина ранга растёт при повторных вставках **между двумя соседними** ключами (драг в одну щель).
Prepend длину **не** растит: он двигает целую часть (`a0 → Zz → Zy`) — важно сказать это вслух,
иначе кажется, что «новые сверху» упрутся в порог постоянно.

Триггер: `length(rank) > 32` или соседи равны. Действие: перенумеровать фазу в плотную сетку
(`generateNKeysBetween(null, null, n)`) в той же транзакции, под тем же локом.

Это тот же примитив, что «нормализуй порядок воркспейса в 1..n» у фаз, только по триггеру, а не
на каждой операции.

### 4.5 Стейл-соседи → 409, не 400

Клиент прислал `afterId`/`beforeId`; за это время их переставили → сервер читает перевёрнутую пару,
`generateKeyBetween` бросает → без обработки это 500.

```
after.rank < before.rank        → норма (соседи не обязаны быть смежными — попадём между)
after.rank >= before.rank       → 409 STALE_NEIGHBORS + рефетч
сосед не найден / из другой фазы → 409 (был верен, мир изменился)
сосед из чужой орги / несуществующий id → 404 / 400
```

Разница смыслов: **400 = «запрос неверен», 409 = «запрос был верен, мир изменился, перечитай»** —
тот же язык, что `WORKSPACE_VERSION_CONFLICT`.

### 4.6 Optimistic lock НЕ вводим

`Workspace.version` защищает **состав конфигурации доски** — там lost update теряет фазу. Здесь
конфликтуют два move разных карточек, которые друг другу не мешают; конфликт двух move одной
карточки — last-write-wins, и это корректно. Version на доску = блокировать всю доску ради
упорядочивания одной карточки.

## 5. Канонический порядок операций внутри `move`

Последовательность жёсткая — иначе реализация разъедется:

```
BEGIN
  advisory_xact_lock(4242, hashtext(toPhaseId))
  прочитать проект (WHERE id = ? AND orgId = ctx.orgId)   → 404 если чужой/нет
  прочитать целевую фазу (composite-FK страхует принадлежность воркспейсу)
  прочитать соседей                                        → 409 если стейл (§4.5)
  rank = generateKeyBetween(after?.rank ?? null, before?.rank ?? null)
  if len(rank) > 32:
      рекомпактнуть фазу → перечитать соседей → сгенерировать заново
  status' = f(phase.type)                                  (§6)
  UPDATE Project SET phaseId, rank, status = …
  if phaseId изменился:
      ActivityRecorder.record(tx, { type: 'project.moved', … })   ← P4
COMMIT
→ ПОСЛЕ коммита: webhook / email (в M1 некуда — границу обозначить комментарием)
```

Проверка длины **до** записи, а не после: иначе редкий путь = 500 `value too long`, а не осмысленный
ответ.

## 6. `status` и ActivityEvent

### 6.1 Синхронизация status ↔ PhaseType

`status` **хранится**, не выводится (`ARCHIVED` — статус без фазы; стабильность к переименованию фазы).
Единственный транзакционный путь синхронизации — `move`:

```
phase.type = OPEN → status = OPEN
phase.type = WON  → status = WON
phase.type = LOST → status = LOST
status = ARCHIVED → move не меняет статус (архив вне доски, §7)
```

`PATCH /projects/:id` статус **не принимает** — иначе появился бы второй путь и синхрон развалился.

### 6.2 ActivityRecorder — здесь он рождается

```ts
ActivityRecorder.record(tx, event); // принимает транзакцию — P4
```

Payload по P2+P3 — **снапшот, без живого FK на Phase**:

```json
{
  "fromPhaseKey": "discovery",
  "fromPhaseName": { "ru": "Дискавери" },
  "toPhaseKey": "contract",
  "toPhaseName": { "ru": "Контракт" },
  "actorName": "Асад"
}
```

Событие переживает удаление фазы — это прямая демонстрация P2 на защите.
Zod discriminated union по `(type, schemaVersion)` в `api-schemas`; вокабула типов общая с
webhook-словарём (M5).

### 6.3 Reorder внутри фазы НЕ пишет событие

Порядок карточки — состояние **представления**, не факт о лиде. Первый аргумент: `ActivityEvent` —
лента проекта (читают люди, RBAC проекта), `AuditLog` (M6, org-scoped, admin-only) — безопасность
и конфигурация; порядок карточек не попадает ни туда, ни туда. Второй (вторичный): зашумление —
реальные события утонут.

Пишутся: `project.created` · `project.moved` (только смена фазы) · `project.archived` /
`project.restored` · `project.updated` (значимые поля: value, owner).

### 6.4 Конкурентные move — два противоречивых события в ленте

**Оба истинны.** Два человека действительно совершили два действия; лента фиксирует факты, а не
финальное состояние (P2). Финальное состояние одно — last-write-wins. Противоречия нет, есть
история конкурентной работы. (Чинить пришлось бы только ленту, которая притворяется текущим
состоянием.)

## 7. ARCHIVED — статус без фазы при NOT NULL `phaseId`

`Project.phaseId` — NOT NULL, значит архивный лид **физически остаётся в фазе**. Следствия, каждое
обязано быть реализовано:

1. **Доска фильтрует `status <> 'ARCHIVED'`** (§8) — иначе архив рисуется на канбане.
2. **Удаление фазы переносит И архивные проекты.** Иначе `onDelete: Restrict` заблокирует удаление
   по невидимой для пользователя причине («фаза пуста», а удалить нельзя). → **§12, проверить в
   сданном срезе.**
3. **Restore:** карточка возвращается в свою фазу, но её ранг мог устареть после рекомпакции →
   на restore **всегда генерируем ранг заново** (наверх колонки), старый не используем.
4. **Архивация/восстановление — события** (`project.archived` / `project.restored`), это факты о лиде.

## 8. Запрос доски — LATERAL + limit на колонку

Два наивных пути, оба плохи: цикл по фазам → N+1 (10 колонок = 10 запросов); один
`WHERE workspaceId = ?` → 10×500 = 5000 строк в ответе.

Канбан не показывает всю колонку — первые ~50 и догрузка. Контракт: `limitPerPhase` + keyset-курсор
`(rank, id)`.

```sql
SELECT ph.id AS phase_id, p.*
FROM "Phase" ph
CROSS JOIN LATERAL (
  SELECT * FROM "Project"
  WHERE "phaseId" = ph.id AND "status" <> 'ARCHIVED'
  ORDER BY "rank", "id"
  LIMIT $2
) p
WHERE ph."workspaceId" = $1
ORDER BY ph."order";
```

**Prisma это не выражает → `$queryRaw`.** Принято осознанно: это **четвёртый выход за границу ORM
и качественно другой, чем предыдущие три** — те были про DDL (`DEFERRABLE`, generated columns,
`REVOKE`), этот про **запрос**. На защите: «я знаю границу абстракции, потому что выходил через неё,
и вот два разных класса причин».

Альтернатива без raw (два запроса: фазы, затем проекты с `ROW_NUMBER() OVER (PARTITION BY phaseId)`)
— тоже требует raw для оконной функции; выигрыша нет.

Догрузка колонки:

```sql
WHERE "phaseId" = $1 AND "status" <> 'ARCHIVED' AND ("rank", "id") > ($2, $3)
ORDER BY "rank", "id" LIMIT $4
```

Keyset, не OFFSET: при неуникальном ранге (§4.2) offset-пагинация недетерминирована.

**Счётчик карточек в колонке (`Discovery · 23`) — отдельный `COUNT`**, из ограниченной выборки он
не выводится.

## 9. Миграция

```prisma
model Project {
  // ...
  rank String @db.VarChar(64)

  @@index([phaseId, rank, id])   // рендер колонки + keyset-курсор
}
```

Порядок — expand/contract в миниатюре (`NOT NULL` сразу упал бы на непустой таблице):

```sql
-- 1. nullable колонка
ALTER TABLE "Project" ADD COLUMN "rank" varchar(64);

-- 2. бэкфилл — СКРИПТОМ (см. ниже), не SQL-выражением

-- 3. NOT NULL после бэкфилла
ALTER TABLE "Project" ALTER COLUMN "rank" SET NOT NULL;

-- 4. MANUAL MIGRATION POINT #4 — байтовая коллация.
--    DO NOT let prisma regenerate: ALTER COLUMN ... TYPE сбрасывает коллацию молча.
ALTER TABLE "Project" ALTER COLUMN "rank" TYPE varchar(64) COLLATE "C";
```

**Бэкфилл — только через библиотеку:**

```ts
for (const { id: phaseId } of phases) {
  const ids = await prisma.project.findMany({
    where: { phaseId },
    orderBy: [{ createdAt: "asc" }, { id: "asc" }],
    select: { id: true },
  });
  if (!ids.length) continue;
  const keys = generateNKeysBetween(null, null, ids.length); // "a0","a1","a2",…
  await prisma.$transaction(ids.map((p, i) => prisma.project.update({ where: { id: p.id }, data: { rank: keys[i] } })));
}
```

> Правило, выведенное из ошибки первого прогона (SQL-бэкфилл `lpad(to_hex(...))` генерировал строки,
> которые **сортируются верно, но не парсятся** библиотекой — голова `'0'` не буква):
> **если формат значения задан библиотекой — бэкфилл генерирует его той же библиотекой**, а не
> SQL-выражением, «которое выглядит похоже».

## 10. Authz и тенантность

- CASL-guard как в срезе фаз (org-роль из свежего `Membership`).
- Любой лукап по id из URL — вместе с tenant-фильтром: `WHERE id = ? AND orgId = ctx.orgId`.
  Иначе IDOR.
- Целевая фаза в `move` — из **того же воркспейса**: composite-FK
  `(phaseId, workspaceId) → Phase(id, workspaceId)` ловит на уровне БД. Задача сервиса — превратить
  FK-violation в **409, не 500** (гонка move-vs-delete-phase, вторая сторона случая из спеки фаз).
- `WorkspaceMember` / `visibility=ASSIGNED` — М6, здесь не используем.

## 11. `fields` — в этом срезе НЕ принимаем

`FieldDefinition` CRUD ещё нет → валидировать значения нечем. Принимать любой JSON = завести данные,
которые потом придётся чинить миграцией. Решение: **`fields` отсутствует в Create/Update-контракте**,
колонка живёт с дефолтом `{}`. Появится вместе с `FieldDefinition` (M2, с блюпринтами).

Откатить это решение дешевле, чем чистить мусор в JSON.

## 12. Ретроспективная проверка сданного среза (сделать ПЕРВЫМ)

`DELETE /v1/phases/:id?reassignTo=…` — проверить, что перенос захватывает проекты **всех статусов**,
включая `ARCHIVED` (§7.2). Если фильтр по статусу есть — это баг: `onDelete: Restrict` заблокирует
удаление фазы, которая с точки зрения UI пуста.

Тест-страж: фаза с одним архивным проектом → `DELETE` без `reassignTo` → 409 с кандидатами;
с `reassignTo` → архивный проект переехал, фаза удалена.

## 13. Порядок реализации

1. **§12** — проверка/фикс переноса архивных при удалении фазы (+ тест).
2. Эмпирическая проверка `fractional-indexing` (§3.1) — зафиксировать факт в ADR.

## 14. Тестирование — что покрыть обязательно

**Ранг и порядок**

- вставка в начало / конец / между / в пустую колонку;
- **50+ подряд вставок в одну щель** → порядок корректен, рекомпакция сработала, длина упала
  (страж от float-мышления и от отсутствия рекомпакции);
- prepend ×100 → длина ранга **не растёт** (подтверждает §4.4);
- равные ранги → `ORDER BY rank, id` детерминирован;
- стейл-соседи (`after.rank >= before.rank`) → **409**, не 500 и не 400;
- сосед из другой фазы → 409; сосед из чужой орги → 404.

**Коллация (manual point #4) — два теста, ловят разное**

- _структурный:_ `SELECT collation_name FROM information_schema.columns WHERE table_name='Project'
AND column_name='rank'` → `'C'`. Краснеет, когда Prisma сбросила коллацию.
- _поведенческий:_ вставить ранги `{'B0','a0'}` → `ORDER BY rank` даёт `['B0','a0']`. Краснеет,
  когда сортировка поехала по любой причине.
- бэкфилл: все существующие ранги парсятся библиотекой (`generateKeyBetween(rank, null)` не бросает).

**Транзакционность (P4)**

- мутация упала → `ActivityEvent` **не** появился;
- move со сменой фазы → событие есть; reorder внутри фазы → события **нет** (страж §6.3);
- событие переживает удаление фазы (payload-снапшот читается, FK нет).

**status и archive**

- move в WON-фазу → `status = WON`; переименование фазы `status` не трогает (P1);
- `PATCH` не принимает `status`/`phaseId`/`rank`;
- архивный проект **не** в ответе доски; restore → новый ранг, наверх колонки.

**Tenant / authz / гонки**

- чужой проект по прямому id → 404; Member на мутации → 403;
- `orgId` из тела игнорируется;
- гонка move-vs-delete-phase → 409, не 500;
- два параллельных move в одну фазу → оба успешны, порядок детерминирован (advisory lock).

**Доска**

- `limitPerPhase` соблюдается по каждой колонке; `hasMore` корректен;
- `total` (COUNT) не равен длине выборки при переполнении;
- keyset-догрузка не дублирует и не теряет карточки на границе равных рангов.
