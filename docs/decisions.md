## Принципы (законы системы)

Каждый выведен из конкретного спора, но применяется везде. На защите: частный вопрос →
ответ через принцип + «и вот ещё N мест, где тот же закон диктует дизайн». Связность важнее
правильности отдельного выбора.

### P1 — Стабильные ссылки

Связи, логика и публичный контракт опираются **только** на стабильные непользовательские
идентификаторы (`id` / `key`). Отображаемые строки (`name`, локализованный текст) — **никогда**
не опора для связи, логики или контракта.

- Следствия: `key ≠ name` · `status` хранится · автоматизации → `key` · blueprint-ссылки → `key`
  · API идентифицирует по `key`/`id`, `name` отдаёт как нагрузку · i18n не задевает опору.
- Окупается дважды: корректность **и** GDPR-erasure (PII single-homed — см. Contact).

### P2 — Пережить источник

Что должно пережить изменение/удаление своего источника — хранит **собственную стабильную
опору** (id или снапшот), а не живую ссылку на мутабельное отображаемое состояние.

- Следствия: `ActivityEvent` = снапшот · история не переписывается при удалении фазы / при merge
  контактов · `actorName` снапшотится (John остаётся John).

### P3 — Минимальный payload

Событие/снапшот хранит минимум, достаточный для восстановления исторического контекста:
метаданные + стабильные ссылки (P1). **Не** тяжёлый/дублирующийся контент.

- Выгода двойная: масштаб append-only таблицы + минимизация PII.

### P4 — Событие атомарно с мутацией

`ActivityEvent` пишется в **той же транзакции**, что и бизнес-мутация. Событие — часть операции,
не сайд-эффект после неё.

- Граница: факты-состояния (event) → **в** транзакции; побочные эффекты (email / webhook /
  embedding) → **после** коммита, через очередь. Против dual-write БД↔очередь — паттерн outbox.

## Manual migration points (расхождения schema.prisma ↔ БД)

Инварианты, не выражаемые в Prisma и живущие в raw SQL. `prisma migrate` может их молча
пересоздать/уронить → латентный баг. Огородить: комментарий-запрет в миграции + тест-на-инвариант.

1. **`Phase(workspaceId, order)` UNIQUE DEFERRABLE INITIALLY DEFERRED.**
   Prisma не умеет DEFERRABLE. Не держим в схеме, чтобы не создался не-deferrable. Тест: два
   дубля order в одной deferred-транзакции → ожидаем violation на commit (падает при регрессии).
2. **`Project` generated columns** под range-фильтры горячих custom fields (`(fields->>'x')::num`).
3. **`ActivityEvent` иммутабельность** — отзыв UPDATE/DELETE у роли приложения.
4. **`Project.rank` COLLATE "C"** — байтовая коллация под fractional-indexing. Механизм риска ДРУГОЙ,
   чем у #1: drift сам не возникает (коллация в файле миграции), но правка типа колонки в схеме
   (`VarChar(64)→VarChar(128)`) заставит Prisma выпустить `ALTER COLUMN ... TYPE`, который **сбрасывает
   коллацию молча**. Тесты: структурный (collation_name='C') + поведенческий (`['B0','a0']` сортируются как есть).
5. **`Contact.company` composite-FK → `ON DELETE SET NULL ("companyId")`** (partial, PG15+).
   `(companyId, orgId) → Company(id, orgId)`, но `orgId` NOT NULL. Prisma выражает `SetNull` только как
   полный `ON DELETE SET NULL` (обе колонки) → при удалении Company пытается занулить и `orgId` →
   падение (эмпирически подтверждено, contacts.md §9.1). Partial-набор колонок Prisma не выражает —
   держим в raw SQL, не давать пересоздать. Тест: delete company при живом контакте → `companyId`
   занулён, `orgId` цел, контакт жив (`delete-integrity.spec`).

> **Смежная правка того же среза (не manual-point, но требует ручного контроля миграции):** D2 —
> `ProjectContact.contact` переведён с `Cascade` на `Restrict` (contacts.md §6). Prisma это выражает,
> но каждый `migrate dev` попутно генерит `DROP INDEX "phase_ws_order_unique"` (#1) — вырезать вручную.

## Project (лид)

**Тенантность — orgId денормализован + composite-FK.**
`orgId` на строке (дешёвый фильтр без join + скоуп RAG позже) **и** composite-FK
`(workspaceId, orgId) → Workspace(id, orgId)` → десинк невозможен на уровне БД.

- Отвергнуто: (а) orgId через join — дорого на каждом запросе; (б) голый orgId без FK — опасно,
  тихий рассинхрон = утечка между тенантами (security-баг, не стилистика).

**Custom fields — трёхуровневая модель, не «JSONB решает всё».**

1. ядро (`value`/`status`) — реальные колонки; 2) узкий набор **доказанно горячих** полу-стандартных
   — generated column + btree (цена: дороже write + диск; не «на всякий»); 3) произвольный хвост — JSON +
   GIN, только equality/contains, **без range/sort**.

- Range-фильтр по произвольному полю в v1 **не даю** — честная цена = рантайм-DDL.
- Reference-поля (`contactRef`): целостность на уровне приложения; dangling толерирую (резолв →
  «удалён»); escape hatch — вынести в `FieldReferenceValue` с FK, если понадобится строгость.
- Unique на произвольных custom-полях **не гарантирую** в БД (потребовал бы per-workspace partial
  index на пользовательское действие); только для core/blueprint-полей.
- Смена типа поля с данными: несовместимую (number→date) **запрещаю**; безопасную (number→text) —
  разрешаю. Иначе — новое поле, старое архивируется.

**`status` хранится, не выводится из фазы.**
Причины: (а) `ARCHIVED` — статус без фазы; (б) стабильность к переименованию фазы (P1: бизнес-статус
≠ имя фазы); (в) дешёвый фильтр «все WON». Синхрон держу единственным транзакционным move-путём.

**`owner` отдельной колонкой (не роль в ProjectAssignee).**
Обоснование — **семантика, не перф**: единственность владельца = инвариант; одна колонка выражает
«ровно один» чище, чем `role=OWNER` в join (там «один OWNER» надо стеречь partial unique).
Перф-аргумент снят: на нашем масштабе join по PK бесплатен. → _Урок: не аргументируй перфом без
профиля; у верного решения обычно есть неперфовая причина._ Эволюция в `ProjectAssignee(role)` при
появлении watcher/contributor.

**`currency` — Char(3) + ISO-4217 в Zod** (не свободная строка: «LOL» недопустим; не enum: ~180 валют).
`source` при этом оставляю **открытым/workspace-конфигурируемым** — осознанно развожу с currency.

**`company` nullable** — один тип обслуживает B2B и B2C; аудиенс = настройка воркспейса, не разные
таблицы.

## Phase

**`order` Int + полная перенумерация в транзакции, НЕ LexoRank.**
Кардинальность O(10) — фракционный ранг окупается на карточках (сотни в колонке), не на колонках.
Один примитив — «нормализуй порядок воркспейса в плотные 1..n из желаемой последовательности» —
обслуживает delete / multi-delete / reorder / blueprint-import разом. Инкрементальные дельты **не**
использую (ветвятся и багуют на batch/import).

- Уникальность+порядок = **инвариант** (в БД, DEFERRABLE — см. manual points). Плотность = опрятность
  (best-effort, чиню в той же транзакции). Дырки инвариант не ломают, но убираю.
- _DEFERRABLE — класс «долг сопровождения», не бесплатная победа_ (см. manual points).

**Reorder-конкурентность — optimistic lock (Workspace.version), не advisory/serializable.**
Конфликты редки (два человека тасуют одну доску — исключение) → цена оптимизма при отсутствии
конфликта = 0. Конфликт → 409 + refetch. Serializable — оверкилл/ретраи; advisory — лок ради лока.

**`key` (иммутабельный слаг) ≠ `name` (LocalizedName, плывёт).**
Три силы тянут `name` — переименование, ребрендинг, i18n — ни одна не трогает `key` (P1). Автоматизации
цепляются за `key`. Генерация: слаг + суффикс при коллизии (`contract-2`) в пределах воркспейса, не UUID
(key обязан оставаться человекочитаемым). Правка `key` не даётся (на него завязаны автоматизации).

**Удаление фазы — `onDelete: Restrict` (БД защищает инвариант «Project не существует без Phase») +
сервисный флоу reassign-then-delete** (FR-WS-4).

**Гонка delete-phase vs move-into-phase — безопасна без явного лока:** Restrict ловит с одной стороны,
FK-violation с другой. Задача сервиса — превратить violation в 409, не 500. (Окупаемость инвариантов-в-БД.)

**`phaseId` на Project, не `projects[]` на Phase:** FK живёт на стороне N связи 1─N — единственный способ
выразить кардинальность.

**orgId на Phase НЕ несу:** тенант-инвариант замкнут транзитивно через Project; потребителя нет;
денормализация без потребителя. (Контраст с Project/ActivityEvent, где потребитель есть — судительность
в обе стороны.)

## Contact / Company

**Дедуп = advisory hint (FR-CC-4), НЕ hard unique.**
email опционален, один email легитимно на нескольких людей (`info@…` — директор/бухгалтер/секретарь),
merge — решение пользователя. Отсутствие UNIQUE — **продуктовое** решение, не упрощение модели.
Индекс на `emailNormalized` (канон, не сырое).

**Гонка при конкурентном создании — не баг.** При soft-дедупе даёт то же, что легитимный «create-anyway».
Дубль **сущности** терпим и сливается; дубль **запроса** (двойной сабмит формы) → idempotency key
(FR-API-5) — другой слой системы. Различать эти два — суть ответа.

**Merge (за пределами MVP-ядра; модель к нему готова).**

- × Activity (P2): история **не** переписывается. События B остаются истинными фактами; merge =
  новое событие-звено, не ластик. Антипаттерн: репойнт `contactId` B→A в старых событиях ради «чистоты».
- × ProjectContact роли: конфликт (A=decision_maker, B=champion в одном проекте) обнажил дефект
  **скаляра** `role`, а не merge → `role` стал `roles String[]`; merge = объединение множеств.
  _Рефлекс: болезненная операция над моделью часто = недоспецификация модели, а не сложность операции._
- Merge-flow (preview + разрешение конфликтов, user-confirmed) отложен; дедуп-хинты в v1.

**Два слоя связи (их путают):** `Contact→Company` (companyId, n-1, org, «где работает») vs
`ProjectContact.roles` (m-n, project, «роль в сделке»). Роль — на связи с проектом, не на контакте.

**nullable composite FK `(companyId, orgId)`:** MATCH SIMPLE → при null не проверяется (B2C ок), при
заданном — орг обязан совпасть. Осознанно.

**GDPR-erasure = тумбстон одной строки Contact.** PII живёт в одном месте (следствие P1 + P3): везде
ссылки по id, в снапшотах — минимум. Стирание распространяется by construction (резолв id → «[удалён]»,
id сохраняю ради целостности ProjectContact и истории). Отдельный принцип «PII single-homed» не завожу —
это следствие P1+P3.

**RBAC-утечка (флаг, не решено в PRD):** Contact org-scoped (идентичность общая между воркспейсами), но
**доступ** к контакту в контексте проекта обязан уважать project-visibility — иначе Member с ASSIGNED
узнаёт о существовании лида/человека мимо своей видимости. Адресная книга org-wide — для ролей выше
Member или со своим скоупом.

**Каскад:** Contact/Company самостоятельны (`onDelete: Cascade` от Org, не от Project) — в отличие от
Task/ActivityEvent (дети Project). Разная экзистенциальная зависимость.

## ActivityEvent

**Scope: лента ПРОЕКТА, не помойка для всего аудита.** `projectId` обязателен, видимость по RBAC проекта.
Org-security-аудит (права/API-ключи/membership, §11.4) → отдельный `AuditLog` (admin-only). PRD внутренне
противоречив (модель project-scoped vs §11.4 org-scoped) — развожу.

**orgId несём** (в отличие от Phase): потребитель есть — org/workspace-аналитика (Scenario C), time-in-phase
(§14), изоляция журнала.

**`payload` = снапшот (P2) + ссылки по key (P1):** `{fromPhaseKey/Name, toPhaseKey/Name}`. Живого FK на
Phase нет — событие переживает удаление фазы. Zod discriminated union по `(type, schemaVersion)`.

**`Json`, не N таблиц:** append-only + читается лентой чаще, чем анализируется по типам → одна широкая
таблица с дешёвой вставкой > 20 специализированных. Типобезопасность не теряется — живёт в api-schemas.

**`schemaVersion`** (следствие P2): факт записан в форме своего времени; фронт читает все поколения событий;
неизвестная пара → graceful fallback.

**`actor`:** `actorId` nullable (SetNull, null=система/ИИ) + `actorName` снапшот (P2) → «John uploaded» и после
John→Jonathan. `actorId` → текущий профиль по клику. Факт историчен, ссылка актуальна.

**`type` строкой + замкнутый словарь в api-schemas** (общий с webhook-вокабулой). Не enum (иначе миграция на
каждый тип).

**Иммутабельность** (§11.4): append-only, app + отзыв UPDATE/DELETE у роли БД (см. manual points).

**Создание — единый `ActivityRecorder.record(tx, event)`, принимает транзакцию (P4).** Не `activity.create`
вразброс по сервисам. Триггер миграции на **domain events**: когда одно действие → много несвязанных реакций
(activity + email + analytics + webhook) → вехи M2/M5.

**Конфликт иммутабельность vs GDPR (§11.4 vs §11.3):** PII в payload не тащим (только id/key + минимум);
право на забвение = тумбстон отображаемых PII-полей, структура события цела.

## Auth (M0)

**Два токена — access stateless JWT + refresh stateful в БД.**
Access — горячий путь (каждый запрос): stateless JWT, проверка подписью без БД (1000 запросов = 1000
проверок без 1000 SELECT). Раз stateless — не отзывается, поэтому короткий (~15 мин). Refresh — холодный
(раз в 15 мин): stateful в БД, отзываемый (logout/кража). Отвергнуто: один долгий stateless JWT — нельзя
отозвать, logout не работает по-настоящему.

**Refresh хранится как SHA-256, НЕ argon2.** Refresh высокоэнтропийный (`randomBytes(32)`) → брутфорс
нерелевантен, медленный хеш дал бы только латентность. Пароль низкоэнтропийный → argon2 (memory-hard).
Различение: медленный хеш — против брутфорса низкоэнтропийных секретов. Клиенту — сырой токен, в БД — хеш
(утечка таблицы не даёт рабочих refresh, как passwordHash).

**Ротация — инвариант «один refresh ровно один раз».** Reuse detection — не отдельная фича, а контроль
инварианта. При reuse убиваем ВСЮ семью (`familyId`), не просто отказываем: нельзя отличить «вор прислал
старый» от «юзер пришёл со старым после ротации вором» → безопасно только kill family + форс-релогин.

**Роль НЕ в JWT, читается из Membership 1 раз/запрос.** Роль в 15-мин токене → stale authorization (понизили
Owner→Member, а он ещё 15 мин Owner). Одна индексная выборка `Membership(activeOrgId,userId)` бесплатна —
оптимизировать против неё = против нуля. Бонус: per-request read ловит исключение из орги мгновенно. JWT
несёт только `{sub, activeOrgId, iat, exp, jti}` — P3 + всё в токене устаревает.

**activeOrgId в токене + switch-org.** Юзер в неск. оргах (Membership m-n); access несёт активную оргу →
ALS-контекст → tenant-скоуп (composite-FK backbone запирает). Смена орги = переиздать access (проверка
membership в целевой орге).

**Хранение: refresh — httpOnly+SameSite=Lax+Secure cookie; access — память JS.** httpOnly против XSS-кражи
refresh; access в памяти (не localStorage) → при XSS утечёт максимум 15-мин токен. SameSite=Lax против CSRF
(httpOnly и SameSite — разные угрозы). CSRF-токен — второй слой позже.

**Logout = revoke RefreshSession; access доживает ≤15 мин.** «Удалить JWT на сервере» нельзя — он stateless,
уже выдан. Поэтому access и короткий.

**Argon2id + progressive rehash.** passwordHash самодостаточен (соль+параметры внутри строки). На логине
`needsRehash()` → пересчёт под новые пороги OWASP прозрачно.

> Полная реализационная стратегия — `docs/specs/auth.md`. RefreshSession — auth-инфра, НЕ CRM-домен;
> не проходила 6 проходов ревью ядра — прогнать отдельно (чистка протухших сессий, лимит сессий на юзера).

**Регистрация создаёт личную оргу (вариант A), НЕ nullable activeOrgId.**
Свежий User без орги → на логине activeOrgId брать неоткуда. Решение: регистрация создаёт личную
Organization + Membership(OWNER) → сирот-без-орги нет by construction, activeOrgId в токене всегда заполнен,
guard одномоделен. Отвергнут вариант B (nullable activeOrgId): спецслучай-null протёк бы во весь guard/JWT-
контракт (две модели авторизации). Инвариант: каждый User имеет ≥1 Membership всегда.

**Слои регистрации: RegistrationService оркеструет, AuthService только аутентифицирует.**
Регистрация — application-сценарий, не auth-операция. RegistrationService держит транзакцию (User + Org +
Membership) и вызывает AuthService.issueTokens(готовый User). AuthService НЕ создаёт бизнес-сущности —
получает готового юзера, занимается паролем/токенами/ротацией. «Личная орга» — тенантная граница онбординга,
не CRM-логика, поэтому auth легитимно её инициирует через домен, не размывая свою ответственность.
Граница P4: User/Org/Membership в tx; будущие эффекты (welcome-email) — после коммита. activeOrgId на логине:
lastActiveOrgId если есть, иначе личная орга.

## Project.rank (порядок карточек в колонке)

**Строковый fractional index (base62), не Int-перенумерация как у Phase.order.** Один вопрос «как хранить
порядок» → разные ответы по кардинальности и частоте вставки в середину: колонок O(10) (перенумерация
дёшева, уникальность — инвариант), карточек сотни (вставка в середину = 1 UPDATE, уникальность НЕ инвариант).
Float отвергнут: `(a+b)/2` исчерпывает мантису за ~50 вставок в одну щель; строка деградирует длиной
(лечится рекомпакцией), а не потерей корректности.

**Библиотека `fractional-indexing`, поведение подтверждено эмпирически** (тест
`fractional-indexing.spec.ts`, не по памяти): `between(null,null)="a0"`; prepend перед первым → заглавная
голова (`"Zz"`) — знак целой части кодируется регистром, поэтому base36-lowercase несовместим и защита
осталась одна (коллация #4, тест на неё несущий); prepend НЕ растит длину (двигает целую часть), вставка
в одну щель — растит (→ рекомпакция по триггеру `len>32`).

**Ранг НЕ уникален, tie-break `ORDER BY rank, id`.** Два одновременных prepend читают один firstRank →
одинаковый ключ; UNIQUE превратил бы безобидную гонку в отказ пользователю (для публичного интейка M5 это
систематика, не редкость). Дубль терпим и лечится — как дедуп контактов. `id` в индексе `(phaseId, rank, id)`
делает скан полностью упорядоченным И служит keyset-курсору.

ADR: RBAC — две оси, в M1 реализована одна

PRD-матрица кодирует ДВЕ независимые оси:
Capability — разрешено ли действие в принципе (роль)
Scope — над какими объектами (visibility: ALL/ASSIGNED)

△ в PRD = capability allowed, scope=ASSIGNED.
M1 реализует ТОЛЬКО capability. Scope временно = ORG.
M6 добавляет visibility-scope как условие на объект в CASL
(can('update','Project',{assigneeId})), НЕ переписывая capability.

Следствие для тестов: тесты M1 проверяют capability
("Member может X"), НЕ org-wide видимость. Последнее временно
и не является контрактом — иначе M6 ломает их массово.

△-строки в M1: capability=allow, scope=ORG (Member работает
во всей орге, сужение до assigned — M6).

Поэтому доступ асимметричен create vs mutate:

ADR: reassign лида — первоклассная операция, не поле PATCH

Матрица: edit lead=Member+, reassign lead=Manager+. Но ownerId —
поле Project, а action-level CASL (can('update','Project')) не видит
полей: дав Member update, PATCH {ownerId} даёт Member право Manager'а.
Это НЕ недосмотр — граница action-level механизма (field-level = другой
уровень гранулярности).

Почему нельзя отложить: ownerId определяет scope в M6 (visibility=
ASSIGNED). Member, переназначив ownerId на себя, в M6 присвоит лид вне
своего scope → field-level дыра M1 = обход visibility в M6. Две оси
смыкаются в уязвимость.

Решение (вариант A): ownerId вычищен из UpdateProjectSchema; reassign —
отдельный эндпоинт POST /projects/:id/reassign под can('reassign',
'Project') (Manager+). Тот же ход, что move вынесен из PATCH: операция с
иной семантикой и правами — отдельный эндпоинт, не поле общего update.
Отвергнуто: field-level CASL (правило под каждое поле, плохо масштаб.)
и проверка в сервисе (прячет authz вне CASL). create по-прежнему
принимает ownerId — начальное назначение при создании ≠ переназначение
существующего лида (последнее и есть охраняемая операция).

ADR: Project.ownerId дефолтится создателем при create (M2, notifications.md)

CreateProjectInput.ownerId остаётся optional, но сервис при отсутствии
явного значения подставляет userId вызывающего: `ownerId: input.ownerId
?? userId`, не голый `input.ownerId`.

Не переоткрывает уязвимость из ADR выше — та защищала ИЗМЕНЕНИЕ ownerId
существующего лида через общий update (Member мог бы присвоить себе чужой
scope); дефолт при СОЗДАНИИ — та же легитимная операция, что и явный
ownerId в create-теле, которую ADR прямо разрешает («начальное назначение
при создании ≠ переназначение»). Роль, создающая лид (Member+), и так
имеет право стать его owner явно — дефолт просто не требует печатать это
руками.

Зачем: без дефолта большинство лидов создаются без owner (create-диалог
его не запрашивает), «уведомить владельца о новом лиде» (notifications.md
§4) вырождается в «уведомить почти никого» — фича выглядит нерабочей не
из-за бага, а из-за пустого поля, которое никто не заполнил. Дефолт решает
это без нового UI и без ослабления reassign-guard'а.

Assignees (co-workers) НЕ дефолтятся аналогично — после дефолта owner
проблема «кого уведомлять» уже решена (owner почти всегда есть), заводить
initial-assignees-at-creation ради того же вопроса было бы решением уже
не существующей проблемы.

ADR: DealRole — Postgres enum сейчас, config-таблица потом (по триггеру)

ProjectContact.roles = DealRole[] (Postgres enum-массив), НЕ String[] и
НЕ config-таблица RoleDefinition.

Почему не String[]: набор ролей в сделке замкнут и доменно осмыслен
(CHAMPION, DECISION_MAKER, ECONOMIC_BUYER, TECHNICAL_BUYER, INFLUENCER,
BLOCKER — B2B-комитет по закупке). String[] пустил бы в БД "champoin" и
любой мусор; enum ловит опечатку на уровне БД (400), а Zod-зеркало —
на входе. Тип = документация набора.

Почему не config-таблица (per-workspace RoleDefinition) сейчас: это
механизм ПОД вторую, несовместимую методологию (напр. другой audience с
принципиально иным набором ролей). Пока audience-набор один и общий —
таблица = пустая абстракция «на будущее» (антипаттерн CLAUDE.md). YAGNI.

Триггер переезда на config-таблицу: появление РЕАЛЬНОЙ второй сущности,
которой нужен свой набор ролей (второй несовместимый audience/методология,
или заказной per-workspace набор). Тогда enum → RoleDefinition, БЕЗ
переписывания потребителей (roles остаётся массивом id/key по P1).

Defense note (особенность enum, знаем и принимаем): расширить enum потом —
ALTER TYPE ADD VALUE — в Postgres НЕ транзакционно и НЕ откатывается.
Для стабильного малого набора это неважно (добавления редки). Но частая
смена набора = прямой аргумент за config-таблицу: там значение — строка
данных, добавляется/убирается обычным INSERT/DELETE в транзакции. Т.е.
«выбрал enum, зная цену расширения; порог боли — частота смен набора».

ADR: тенант-изоляция через явный orgId, не ALS

M0 заложил TenantContextInterceptor + ALS (currentTenant()) как задел под
data-access скоуп. M1 де-факто пошёл через ЯВНЫЙ параметр
(findByIdInOrg(id, orgId), where:{orgId}). Выбор зафиксирован в пользу явного:

(1) виден в сигнатуре — компилятор не даёт забыть orgId; ALS-скоуп невидим в
    сигнатуре и тихо отваливается вне HTTP-контекста;
(2) BullMQ-воркеры (M4) выполняются ВНЕ запроса — интерсептор там не срабатывает,
    currentTenant() вернул бы пусто/чужое, orgId всё равно пришлось бы передавать
    явно. Значит ALS не дожил бы до M4 → было бы два механизма (ALS для HTTP,
    явный для воркеров). Явный везде — консистентнее и переживает async-границу.

ALS-задел (TenantContextInterceptor, tenantStorage, currentTenant, TenantContext)
удалён как незавершённая параллельная реализация, не мусор — осознанный выбор
единого механизма. При переезде на Postgres RLS (M6+) тенант уйдёт на уровень
БД — тогда пересмотреть.

ADR-FE-1: TanStack Router вместо зафиксированного React Router

PRD §12.3 / CLAUDE.md пинили React Router. Фронт (frontend-architecture.md §4)
отклоняется на TanStack Router. Причины:
- client-heavy SPA-дашборд; типизированные search-params под фильтры доски,
  которые держим в URL;
- общий кэш и паттерн мутаций с уже выбранным TanStack Query;
- end-to-end типобезопасность путей/params без codegen.

React Router v7 раскрывает типобезопасность только в framework-mode/SSR. Helix —
SPA, деплой статикой на CDN, SSR нет → в library-mode остались бы с ручным
приведением search-params. Цена: экосистема меньше, расхождение с PRD-стеком.
Принято.

Полное обоснование и производные решения (loader = только прогрев кэша,
file-based роуты, pathless-группировка) — frontend-architecture.md §4.
