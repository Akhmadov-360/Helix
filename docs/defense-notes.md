# Helix — Защитные заметки (Defense Notes)

> **Как пользоваться.** Это документ для **устной** защиты — ответы на «почему?», которые
> надо уметь развернуть вслух, не подглядывая. Возвращаюсь сюда перед защитой и **проговариваю
> каждый пункт вслух своими словами**. Если пункт не разворачивается в речь — это пробел, туда копать.
> Канонические формулировки и полный контекст — в `decisions.md`; здесь — рабочая, «моя» версия.

---

## Принципы (законы системы)

**P1 — Стабильные ссылки.** Связи, логика автоматизаций и публичный API опираются строго на
неизменяемые ключи (`id`/`key`), никогда на отображаемое имя (`name`). Пользователь может переименовать
фазу или переключить язык — `key` (`"proposal"`) стоит, `name` (LocalizedName) плывёт. Автоматизация,
завязанная на имя, сломалась бы при переименовании; завязанная на `key` — нет.

**P2 — Пережить источник.** Событие в истории — записанный факт прошлого. История не переписывается и
не теряется, даже если источник (актор, фаза, контакт) потом изменён/удалён. Поэтому в событие пишется
**снапшот на момент времени** (`actorName: "John"`, `fromPhaseKey`, `toPhaseKey`), а не живой FK.

**P3 — Минимальный payload.** В снапшот кладём минимум: метаданные + стабильные ссылки, не тяжёлые
объекты. Две выгоды: (1) `ActivityEvent` — append-only на миллионы строк, дублировать тяжёлый JSON =
переполнить диск; (2) меньше копий PII → проще GDPR-удаление.

**P4 — Событие атомарно с мутацией.** Запись `ActivityEvent` — в **той же транзакции**, что и бизнес-
изменение. Побочные эффекты (email, webhook, эмбеддинги) — **после коммита**, в очередь (BullMQ).
Граница: факт-состояние → в транзакцию; эффект во внешний мир → в очередь.

## 1. Project (Лид / Сделка) — центральная сущность

### Мультиарендность — orgId на строке + composite-FK

Три такта, как отвечать:

1. **Зачем orgId прямо на Project** (а не только через `workspace.orgId`): фильтр по тенанту одним
   `WHERE orgId = ...` **без join на самом горячем пути** — а фильтр по тенанту стоит буквально на каждом
   запросе к Project. Плюс скоуп для RAG/vector-search позже (эмбеддинги фильтруются по orgId напрямую).
2. **Чем опасно просто продублировать orgId**: из-за бага в коде или ручного `UPDATE` может появиться
   карточка, где `Project.orgId = Org_A`, а `workspaceId` указывает на доску из `Org_B`. Данные `Org_B`
   утекут в контекст `Org_A` — критический security-инцидент для B2B SaaS.
3. **Как заперли**: обычный FK `workspaceId → Workspace.id` гарантирует только, что воркспейс
   _существует_, про orgId он не знает. А composite-FK **`(workspaceId, orgId) → Workspace(id, orgId)`**
   требует, чтобы **пара совпала** с реальной строкой Workspace. Записать Project с orgId, не равным orgId
   его воркспейса, БД физически откажется. Рассинхрон невозможен на уровне базы, а не «проверяем в сервисе
   и надеемся».

> Ловушка: «зачем `@@unique([id, orgId])` на Workspace, id же и так PK?» → **не ради уникальности** (id
> уникален), а чтобы **открыть пару `(id, orgId)` как валидную цель составного FK**. Без этого unique
> composite-FK в неё не объявить.

### Трёхуровневые кастомные поля (`Project.fields`)

- **Ядро** (`value`, `status`) — обычные SQL-колонки. Быстро, строго, типизировано.
- **Горячие кастомные поля** — **материализованные (STORED) generated columns** + B-tree индекс. Только
  для полей, по которым доказанно нужны диапазоны/сортировка (`budget > 5000`). Цена: STORED физически
  лежит на диске и пересчитывается на каждый write → дороже запись + место. Поэтому **только для доказанно
  горячих**, не «на всякий случай». (Важно: по _virtual_-колонке B-tree не построить — потому STORED.)
- **Хвост произвольных полей** — JSONB + GIN-индекс. Только equality/contains (точное совпадение / наличие
  тега), **без range/sort**.

**Главный вывод:** диапазонную фильтрацию по _любому_ произвольному полю в v1 не даю — честная цена этого
= менять структуру БД на лету (DDL в рантайме), что уронит базу под нагрузкой. Модель кастомных полей —
это спектр компромиссов (колонки → STORED generated → JSON+GIN), а не «JSONB решает всё».

### `status` хранится, а не выводится из фазы

- `ARCHIVED` — статус **без** фазы, из фазы его не вывести.
- Стабильность к переименованию: пользователь переименует «Успешно» → «Победа», бизнес-статус `WON` не
  должен сломаться (P1: статус ≠ имя фазы).
- Дешёвый фильтр «все WON» по одному полю без join к фазам.
- Синхрон держу **единственным транзакционным move-путём**: сдвинул `phaseId` + обновил `status` + записал
  событие — атомарно. Прямой записи в `status` нет.

### `ownerId` отдельной колонкой (не роль в ProjectAssignee)

Причина — **семантика, не перф**. Единственность владельца = инвариант: у сделки ровно один ответственный.
Одна колонка `ownerId` выражает «ровно один» чисто; `role = OWNER` в таблице участников потребовал бы
стеречь partial-unique, чтобы не появилось два владельца. Перф-аргумент снят: join по PK бесплатен на нашем
масштабе. Эволюция в `ProjectAssignee(role)` — когда появятся watcher/contributor.

> Урок себе: не аргументировать перфом без профиля; у верного решения обычно есть неперфовая причина.

### `currency` — строго, `source` — открыто (осознанно развожу)

- `currency` — `Char(3)` + валидация ISO-4217 в Zod. Не свободная строка (иначе пройдёт «LOL»), не
  Postgres enum (~180 валют, миграция на каждую правку списка). Множество замкнуто, но большое и внешне-
  стандартное → строка с валидацией в коде.
- `source` («website», «referral») — **открытое, workspace-конфигурируемое**. Множество растёт в рантайме,
  задаётся пользователем → enum был бы кандалами (каждый новый источник = миграция).

> Готовый ответ на «почему тут строго, а рядом свободно?»: инструмент под **природу множества** —
> замкнутое+стабильное+задаёт разработчик → enum; большое (currency) / пользовательское (source) → строка.

### `company` nullable

Один тип `Project` обслуживает и B2B, и B2C. Аудиенс — это **настройка воркспейса**, а не две таблицы
(`B2BProject`/`B2CProject`). В B2C `companyId = null`, логика одна и та же.

## 2. Phase (колонка доски)

### `order` Int + полная перенумерация в транзакции (НЕ LexoRank)

Порядок — обычное целое. Любая операция, меняющая состав/порядок (delete / multi-delete / reorder /
blueprint-import), заканчивается **полной перенумерацией фаз воркспейса в плотные 1..n одной транзакцией**,
из желаемого порядка. Не инкрементальные дельты (они ветвятся и багуют на batch/import).

- **Почему не LexoRank/дробные ранги:** фракционный ранг окупается на **карточках** (сотни в колонке), а
  колонок — десятки. Кардинальность O(10) → переписать все строки всегда дешевле и корректнее, чем считать
  минимальную дельту. Один примитив «нормализуй порядок в 1..n» закрывает все четыре сценария разом.
- **Уникальность+порядок = инвариант** (в БД, DEFERRABLE — см. ниже). **Плотность = опрятность**
  (best-effort, чиню в той же транзакции). Дырки в order (`1,2,4,5` после удаления 3) инвариант **не**
  ломают — сортировка `ORDER BY order` корректна, — но убираю перенумерацией, чтобы order не рос неограниченно.

### Reorder-конкурентность — optimistic lock (`Workspace.version`)

Два человека тасуют одну доску — редкое исключение. Оптимистичная блокировка: оба читают `version=5`,
первый коммитит → `version=6`, второй получает **409 Conflict** → клиент перезапрашивает свежую доску.
Цена оптимизма при отсутствии конфликта = 0 (никаких локов). Serializable — оверкилл/ретраи; advisory —
лок ради лока.

### `orgId` на Phase НЕ несу (контраст с Project/ActivityEvent)

- **Нет прямого потребителя:** нет сценария «все фазы организации в обход воркспейсов». Фазы всегда
  читаются в контексте одной доски (`workspaceId`).
- **Инвариант замкнут транзитивно:** `Project` заперт к своему `Workspace` через `(workspaceId, orgId)` и
  к `Phase` через `(phaseId, workspaceId)` → фаза гарантированно в воркспейсе правильного орга **через
  Project**. Утечка исключена без orgId на самой Phase.
- **Вывод:** денормализация без реального потребителя = лишний мусор в схеме + долг поддержки.

> Это **пара** к «orgId на Project несём». Критерий один: **есть ли потребитель?** На Project — да (горячий
> фильтр + RAG). На ActivityEvent — да (org/workspace-аналитика, time-in-phase, изоляция журнала). На Phase —
> нет. Судительность в обе стороны, а не «денормализуй везде».

### `key` (иммутабельный слаг) ≠ `name` (LocalizedName)

`key` (`"proposal"`) создаётся один раз, не меняется — за него цепляются автоматизации/блюпринты. `name`
(`{ru: "КП", en: "Proposal"}`) меняется хоть 10 раз в день — логика не падает (P1). Три силы тянут `name`
(переименование, ребрендинг, i18n) — ни одна не трогает `key`. Генерация: слаг + суффикс при коллизии
(`contract-2`) в пределах воркспейса, не UUID (key обязан быть человекочитаемым). Править `key` нельзя.

### DEFERRABLE-уникальность порядка — «долг сопровождения»

`UNIQUE(workspaceId, order) DEFERRABLE INITIALLY DEFERRED` — БД проверяет уникальность **на COMMIT**, а не
на каждом UPDATE. Это даёт и жёсткий инвариант, и безопасную перенумерацию (в середине транзакции временные
дубли order допустимы). Prisma DEFERRABLE не умеет → живёт в raw-SQL миграции.

> Хвост честности: это расхождение `schema.prisma ↔ БД`. `prisma migrate` может молча пересоздать constraint
> без DEFERRABLE → латентный баг. Огородить: комментарий-запрет в миграции + пункт в ADR + тест-на-инвариант
> (два дубля в deferred-транзакции → violation на commit; падает при регрессии). «ORM не умеет из схемы» —
> не повод ослаблять инвариант, а повод спуститься в raw SQL и огородить.

### Удаление фазы + гонка «delete-vs-move»

`onDelete: Restrict` на связи Project→Phase: **БД защищает инвариант «Project не существует без Phase»**
(формулировка через инвариант, не через «нельзя удалить»). Сервисный флоу: сначала перенос карточек в
другую фазу, потом удаление пустой.

**Гонка** (А удаляет пустую фазу, Б в ту же секунду тащит карточку в неё) — безопасна **без явного лока**:

- **Первым успел DELETE:** фаза исчезла → move Б пишет `phaseId` несуществующей фазы → **FK-violation** →
  rollback Б. Клиент получает 409 (`PHASE_DELETED`), перерисовывает доску, возвращает карточку.
- **Первым успел MOVE:** в фазе появился ребёнок → DELETE А ловит **Restrict-violation** → rollback А.
  Клиент получает 409 (`PHASE_NOT_EMPTY`).

Оба исхода безопасны, потому что инварианты в БД ловят гонку с обеих сторон — не нужны ручные
`SELECT ... FOR UPDATE`. Задача сервиса — превратить violation в осмысленный **409, а не 500**.

> Тонкости для добивки: (1) обе ошибки формально FK-violation (Postgres 23503 / Prisma `P2003`), но операция
> разная — сервис знает, делал он move или delete, и мапит на нужное сообщение **по контексту вызова**, а не
> по коду. (2) `Restrict` не конфликтует с каскадом воркспейса: при удалении воркспейса проекты каскадно
> удаляются **раньше** фаз, к моменту удаления фазы детей уже нет. Restrict бьёт только по **прямому** удалению
> фазы из-под живых проектов.

## 3. Contact & Company (клиенты)

### Дедуп = advisory hint, НЕ hard UNIQUE

Отсутствие `UNIQUE(email)` — **продуктовое** решение, не упрощение.

- Email не гарантирует уникальность человека: `info@company.com` легитимно у директора, бухгалтера,
  секретаря — три реальных контакта.
- Hard UNIQUE вернул бы **409** там, где по бизнесу конфликта нет — заблокировал бы легитимное создание.
- Soft-dedup: терплю дубли сущности, подсвечиваю подсказкой («кажется, такой контакт уже есть»), решение о
  merge — за пользователем. Индекс на **`emailNormalized`** (канон: lowercase/trim), не на сыром email.

### Гонка при конкурентном создании — НЕ баг (различаю два слоя)

Два запроса создают контакт с одинаковым email → два контакта. **Это не баг** — при soft-дедупе даёт то же,
что легитимный «create-anyway». Ключ — **намерение источника (intent)**:

- **Легитимный дубль сущности** (менеджер А ввёл руками, менеджер Б импортировал из CSV — два разных
  намерения) → нормальная жизнь CRM. Решается на **продуктовом слое**: hints + UI merge.
- **Двойной сабмит формы** (один клиент, один клик, но ушло два HTTP из-за лага) → баг **транспортного
  слоя**. Решается **idempotency-key** (FR-API-5): второй запрос с тем же ключом не выполняется повторно, а
  возвращает ответ первого.

Каждая проблема — на своём слое. UNIQUE не лечит двойной клик; idempotency не лечит легитимные дубли.

> Добивка: idempotency сам не создаёт новую гонку — ключ хранится (Redis, TTL), проверка «видел ли ключ»
> атомарна через `SET NX` (запиши, только если ключа нет — одна атомарная команда).

### Merge + `roles String[]`

- **`roles` — массив** по двум причинам сразу: в **одной** сделке человек может быть и Decision Maker, и
  Champion; и это же делает объединение контактов чистой операцией — **Set Union** множеств ролей.
- **История не переписывается (P2):** при merge не лезу в старые `ActivityEvent` менять `contactId`. Событие
  «Mary создала контакт B» осталось истинным фактом. Merge = **новое** событие-звено, не ластик по старым.
- Merge-flow (preview + разрешение конфликтов, user-confirmed) — за пределами MVP; модель к нему готова.

> Рефлекс: болезненная операция над моделью (merge) часто = **недоспецификация модели** (скаляр `role`), а не
> сложность операции. Починил модель (`role → roles[]`) — операция выпрямилась.

### Два слоя связи (их путают)

- **`Contact → Company`** (`companyId`, n-1, org-уровень) — «чей это сотрудник». Глобальный факт о человеке.
- **`ProjectContact.roles`** (m-n, project-уровень) — «функция в **этой** сделке». Один человек в сделке А —
  Champion, в сделке Б — Decision Maker.

Роль живёт на **связи с проектом**, а не на контакте, потому что **атрибут живёт на том уровне, на котором
он меняется**: меняется от сделки к сделке → на `ProjectContact`. Если бы роль висела на `Contact` (одно
поле на человека), она не смогла бы выразить две разные роли в двух сделках — модель бы сломалась.

### GDPR-erasure = тумбстон одной строки Contact

Вся PII (имя, email, phone) живёт **только** в таблице `Contact` — и это **следствие P1 + P3**: везде
ссылаюсь по `id` (P1), в снапшоты кладу минимум (P3), значит копий имени по БД нет. Поэтому удаление = стереть/
анонимизировать **одну строку** Contact (id сохраняю ради целостности ProjectContact и истории). Стирание
распространяется by construction: любой резолв id → «[Удалённый контакт]». Карточка проекта и история не рушатся.

### RBAC-утечка через контакт (флаг, не полностью решено)

**Корень проблемы:** `Contact` и `Project` живут на **разных уровнях изоляции** — контакт org-scoped
(общая идентичность), проект record-scoped (`visibility=ASSIGNED`). Дыра — в **шве** `ProjectContact` между
широко-видимой и узко-видимой сущностями.

**Сценарий:** Менеджер А (`ASSIGNED`) в общей адресной книге видит «Иван Петров» и через связанные проекты
/ автокомплит узнаёт, что Иван привязан к секретной сделке менеджера Б. Даже не открыв саму сделку, А узнал
**факт её существования** (information disclosure через метаданные) → риск увода клиента, нарушение
конфиденциальности M&A/тендеров.

**Купирование:**

1. Связанные проекты в карточке контакта фильтруются той же visibility-логикой, что и прямой доступ к
   проектам — на **сервере**, не в UI (UI-скрытие косметическое). Контакт не становится обходным каналом.
2. Общий реестр контактов (адресная книга org-wide) — для ролей выше Member или с `visibility=ALL`; для
   `ASSIGNED` — режим «поиск только при привязке».

> Честный остаток: **дедуп-хинт** сам по себе — тонкая утечка (ввёл email → «контакт существует» = узнал
> факт существования). Полностью закрыть, не сломав дедуп, трудно. Вижу проблему до конца, а не до первого слоя.

### Каскад — разная экзистенциальная зависимость

`Contact`/`Company` самостоятельны: `onDelete: Cascade` от **Org**, не от Project (адресная книга существует
без сделок). В отличие от `Task`/`ActivityEvent` — они дети `Project`, без него не существуют.

## 4. ActivityEvent (лента событий + аудит)

### Scope — лента ПРОЕКТА, не помойка для всего аудита

`projectId` обязателен, видимость по RBAC проекта. Глобальный security-аудит (кто менял права/API-ключи/
membership) → **отдельная таблица `AuditLog`** (admin-only). PRD внутренне противоречив (модель project-scoped
vs §11.4 org-scoped) — сознательно развожу две заботы.

### `Json`, не 20 таблиц

Append-only журнал: только дописывают, читают лентой по времени (не анализируют по типам). Одна широкая
таблица с `payload` Json + дешёвая вставка > 20 специализированных. Типобезопасность не теряется — живёт в
`api-schemas` (Zod discriminated union).

### `schemaVersion` (следствие P2)

Событие 2024 записано в форме V1, 2026 — в V2. Факт записан в форме **своего времени**; фронт читает все
поколения, неизвестная пара `(type, schemaVersion)` → graceful fallback.

### P4 — событие в транзакции, эффекты в очередь

**Событие — в той же транзакции, что и мутация.** Если карточка передвинута — запись в ленте **обязана**
появиться; либо оба, либо ничего (rollback). **Email/webhook — строго ПОСЛЕ коммита, в очередь.** Что ломается
при перестановке:

- **Email внутри транзакции:** (1) HTTP к почте зависает 3с → транзакция держит строки и коннект 3с → под
  нагрузкой пул соединений исчерпан → весь бэкенд встал (504). (2) Письмо улетело, потом транзакция
  откатилась → клиент получил письмо о событии, которого не было. **Внешний мир нельзя откатить ROLLBACK-ом.**
- **Событие после коммита:** коммит прошёл, процесс упал до `activityEvent.create()` → сделка изменилась,
  истории нет → аудиторский след потерян.

Итог-критерий: **факт (ACID-совместим) → в транзакцию; эффект во внешний мир (не откатывается, зависит от
сети) → в очередь (BullMQ).** Этим критерием классифицирую любую новую операцию.

> Тонкости: (1) если payload невалиден (битый JSON) при событии-в-транзакции → откатывается **вся** операция,
> карточка не двинется без записи в истории — это **правильно** (нет валидного факта → нет мутации), а не
> «битое состояние». (2) «email после коммита» сам по себе — **dual-write** между БД и очередью (коммит прошёл,
> процесс упал до постановки в очередь → письмо не уйдёт). Полное решение — **transactional outbox**: в той же
> транзакции пишу и событие, и строку в `outbox`; воркер разгребает outbox → в очередь. Тогда «факт записан» и
> «эффект запланирован» атомарны.

### Единый `ActivityRecorder.record(tx, ...)` + `type` строкой

**Почему единый рекордер, а не `activityEvent.create()` в каждом сервисе:** чтобы инварианты записи
(транзакция P4, снапшот актора P2, минимум PII P3, `schemaVersion`) жили в **одном** месте, а не повторялись —
и не забывались — в двадцати сервисах. Единственный путь записи = единственное место, где эти правила можно
нарушить, значит единственное, которое надо проверить.

> Добивка «почему не domain events?»: это **целевая** архитектура (сервис публикует `ProjectMoved`,
> `ActivityHandler` подписан). Триггер перехода — когда одно действие → **много несвязанных реакций**
> (activity + email + аналитика + webhook), вехи M2/M5. Сейчас рекордер централизует запись без накладных
> расходов шины. Знаю, куда растёт; выбрал промежуточное по скоупу, а не по незнанию.

**Почему `type` — строка, а не Postgres enum:** enum потребовал бы DDL-миграции на **каждый** новый тип
события (а их добавляет каждая фича). Строка + **замкнутый словарь в `api-schemas`** — гибко в БД, строго в
коде. Плюс: это тот же **общий словарь**, что у webhook-событий (`lead.created`, `lead.phase_changed`), —
один словарь на двух потребителей. И `type` в паре с `schemaVersion` работает **дискриминатором** Zod-union:
по паре фронт выбирает схему payload. Enum дал бы валидацию значения, но не эту гибкую типизацию payload.

### PII в логах

В `payload` не пишу личные данные (телефоны, адреса, пароли) — только id/key + изменившиеся статусы (P3).
Поэтому при GDPR-удалении контакта лог событий чистить **не нужно** — копий PII там нет.

> Уточнение: «Zod защищает от PII» — неточно. Zod проверяет **форму** payload (что поля те и типы те); он не
> знает, что «имя» — это PII. Не-включение PII — это **дисциплина того, что я туда кладу** (P3), а не магия
> валидатора.

## 5. Валидация входа (Zod-пайп) — per-route, НЕ глобальный `APP_PIPE`

Схема цепляется к эндпоинту явно: `@Body(new ZodValidationPipe(createProjectSchema))`. Схема — из
`api-schemas` (schema-first: сначала `*Schema`, потом импорт в контроллер).

- **Явность контракта:** глядя на контроллер, сразу видно, какой схемой валидируется вход — это и
  документация, и защита ревьюером за секунду. Не «где-то в глобальной магии».
- **Почему не `APP_PIPE`:** Nest-пайпы не получают `ExecutionContext`/`Reflector` (только `ArgumentMetadata`)
  → глобальному пайпу нечем привязать схему без DTO-**метатипа**. А DTO-классы мы не используем (конвенция:
  НЕ class-validator). Глобальная валидация потребовала бы либо DTO-классов (ломает конвенцию), либо
  `@ValidateBody` + метадата + интерсептор (два механизма ради иллюзии «одной регистрации»). Оба хуже.
- **Ошибки атомарно с выходом:** `schema.parse` бросает `ZodError` → единый `AllExceptionsFilter` → `400
VALIDATION_ERROR` с `fieldErrors`. Валидация не размазана по контроллерам.

## 6. Auth (аутентификация M0)

### Два токена: зачем и в чём разница

- **Access** — JWT, stateless, ~15 мин. Проверяется подписью, БЕЗ похода в БД. Это горячий путь: 1000
  запросов = 1000 проверок подписи без 1000 SELECT — **JWT это оптимизация самого частого пути**.
- **Refresh** — непрозрачный токен, stateful в БД, ~7–30 дней. Используется редко (раз в 15 мин), поэтому
  поход в БД на нём допустим (холодный путь).
- **Почему не один долгий JWT:** stateless нельзя отозвать. Если access короткий — украли, протухнет за 15
  мин. Если бы он был долгим — logout не работал бы по-настоящему, кража жила бы до истечения.

### Почему access вообще JWT, а не строка в таблице

Любимый вопрос. Ответ инженерный: access на **каждом** запросе. Таблица = SELECT на каждый запрос. JWT =
проверка подписи, ноль SELECT. Оптимизация горячего пути. Refresh редкий → ему таблица по карману.

### Как отзываю access при logout

Никак напрямую — «удалить JWT на сервере» нельзя, он stateless и уже выдан. **Logout = revoke
RefreshSession** (ставлю `revokedAt`). Старый access доживает ≤15 мин и протухает сам. Это нормально — и
ровно поэтому access короткий. Многие новички пытаются «удалить JWT на сервере» — так нельзя.

### Refresh хранится хешем — и почему SHA-256, а не argon2

Если утечёт БД, никто не должен смочь использовать refresh — как с `passwordHash`. Поэтому в БД лежит
**хеш**, клиенту отдаём сырой токен. Но хеш **быстрый (SHA-256)**, не argon2:

- **Пароль** низкоэнтропийный (человек придумал) → брутфорсится → нужен медленный memory-hard argon2.
- **Refresh** высокоэнтропийный (`randomBytes(32)`) → брутфорс нерелевантен → медленный хеш дал бы только
  латентность на каждом refresh. Быстрый корректен именно из-за энтропии.

### Ротация и reuse detection — это ОДИН инвариант

Инвариант: **один refresh используется ровно один раз.** После использования `refresh_1 → refresh_2` старый
`refresh_1` обязан умереть. Если он приходит снова — аномалия. То есть reuse detection не отдельная фича, а
**контроль инварианта**. Чтобы его проверять, БД помнит, что токен уже потрачен (`usedAt`), и вся цепочка
ротаций носит один `familyId`.

### Почему при reuse убиваю ВСЮ семью, а не просто отказываю

Пришёл старый `refresh_A`, хотя уже был `refresh_B`. Два возможных сценария:

1. Настоящий юзер обновил токен → вор украл старый.
2. Вор первым использовал refresh → настоящий юзер позже пришёл со старым.

**Отличить невозможно.** Поэтому единственное безопасное действие — убить всю цепочку (`familyId`) и
заставить перелогиниться. Простой отказ не спасает: если ротировал вор, у него на руках свежий валидный токен.

### Роль НЕ в JWT (тут я спорил и выбрал компромисс)

Если положить `role` в токен → **stale authorization**: понизили Owner→Member, а в 15-мин токене всё ещё
Owner. Мой выбор: JWT несёт `{userId, activeOrgId}`, а **роль читается из Membership один раз за запрос**.

- Membership читается 1 раз/запрос (не на каждую строку) — одна индексная выборка бесплатна.
- Зато смена роли вступает в силу **сразу**, а не через 15 мин.
- Бонус: тот же per-request read ловит **исключение из орги мгновенно** (нет membership → отказ сразу).

### Что вообще в JWT

Только для авторизации: `{sub/userId, activeOrgId, iat, exp, jti}`. **НЕ** role (устаревает), **НЕ**
email/name/avatar (P3 + устаревает; профиль — отдельным `/me`). `jti` — id токена, копейки сейчас, задел под
audit/tracing/blacklist.

### Юзер в двух оргах — как не дать чужие данные

`activeOrgId` в токене → guard кладёт в ALS-контекст → все запросы скоупятся по нему, а **composite-FK
backbone физически запирает** данные к этой орге. Смена орги = `switch-org` (проверка membership) →
переиздать access с новым `activeOrgId`.

### httpOnly cookie — а CSRF?

**httpOnly и SameSite решают РАЗНЫЕ угрозы, не путать:**

- httpOnly → JS не прочитает cookie → защита от **XSS-кражи** refresh.
- SameSite=Lax → cookie не шлётся на cross-site POST → защита от **CSRF** (а CSRF это и есть cross-site POST
  на мой `/refresh`).
- CSRF-токен (`X-CSRF-Token`) + Origin/Referer — второй слой, когда появятся сложные формы. В M0 Lax хватает.

### argon2 — два нюанса

1. `passwordHash` самодостаточен: соль и параметры (`m,t,p`) внутри строки `$argon2id$...`. Отдельно не хранить.
2. **Progressive rehash:** на логине после `verify()` → `needsRehash()`; если OWASP поднял пороги —
   пересчитать хеш прозрачно (открытый пароль на руках только в этот момент). Юзера не заставляем менять пароль.

### Остаточные углы (честно назвать, если спросят)

- **Окно толерантности к сетевому ретраю:** плохой интернет → повтор refresh выглядит как reuse → ложный
  разлогин. В M0 строгая политика (любой старый = reuse). Окно (~5–10с, та же сессия, цепочка не поехала) —
  позже; это дубль **запроса** (сеть) vs reuse **токена** (атака).
- **Чистка протухших сессий / лимит сессий на юзера** — RefreshSession auth-инфра, не проходила ревью ядра;
  прогнать отдельно.
