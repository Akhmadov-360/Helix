# Helix — Памятка по архитектуре и решениям (ADR Lite)

> **Как пользоваться:** Этот документ содержит ответы на вопрос «ПОЧЕМУ?» для защиты архитектуры Helix перед тимлидом/ревьюером. Каждый принцип и решение выведены из реальных инженерных ограничений.

---

## Блок 1. Принципы системы (Законы Helix)

### P1 — Стабильные ссылки (Stable References)

- **Идея:** Все связи в БД, логика автоматизаций, бизнес-правила и публичные API опираются **строго на уникальные ключи (`id` / `key`)**, но **никогда** на отображаемые пользователю текстовые названия (`name`).
- **Почему так:**
  - Пользователь в любой момент может переименовать колонку (Phase) с `"Discovery"` на `"Первичный звонок"` или переключить язык UI (узбекский / русский / английский).
  - Если автоматизация (например, _«при входе в фазу X отправить email»_) завязана на имя `"Discovery"`, она мгновенно сломается при переименовании.
- **Следствие:** `key` не меняется никогда (`"discovery"`), а `name` — это просто текстовая обертка для UI (LocalizedName).

---

### P2 — Пережить источник (Survive the Source)

- **Идея:** События в истории (`ActivityEvent`) — это записанные факты прошлого. История **не переписывается и не удаляется**, даже если источник события (пользователь, колонка или контакт) был изменен или удален.
- **Почему так:**
  - Если менеджер _John_ перенес карточку в фазу _"Proposal"_, а через неделю _John_ сменил имя на _Jonathan_, удалился из системы или была удалена сама фаза _"Proposal"_, история не должна поехать или потерять данные (`null`).
- **Следствие:** В `ActivityEvent` пишется **снапшот (снимок) данных на момент времени**: `actorName: "John"`, `fromPhaseKey: "call"`, `toPhaseKey: "proposal"`.

---

### P3 — Минимальный payload (Minimal Payload)

- **Идея:** В события и снапшоты мы записываем **только минимально необходимый контекст** (метаданные + стабильные ссылки + измененные минимальный снимок нужных полей), а не тяжелые объекты целиком.
- **Почему так:**
  1. **Размер БД:** `ActivityEvent` — это append-only таблица (в нее только пишут миллионы строк). Если дублировать тяжелый JSON (например, весь текст документа на 50 страниц), диск быстро переполнится.
  2. **Приватность / GDPR:** Чем меньше копий персональных данных (PII) разбросано по логам, тем проще потом удалить данные о клиенте по запросу.

---

### P4 — Событие атомарно с мутацией (Atomic Events)

- **Идея:** Запись события в `ActivityEvent` происходит **в той же SQL-транзакции**, что и само изменение бизнеса (например, движение карточки `Project`). А вот побочные эффекты (Email, Webhooks, RAG-эмбеддинги) выносятся **ЗА пределы транзакции в очередь (BullMQ)**.
- **Почему так:**
  - Если упадет запись в `ActivityEvent`, должно откатиться и изменение проекта (данные останутся целостными).
  - **Почему нельзя отправлять Email/Webhook прямо в транзакции?** Если внешний сервис (SendGrid, сторонний сервер) зависнет на 10 секунд, наша SQL-транзакция заблокирует строки в Postgres на 10 секунд, и система мгновенно ляжет под нагрузкой.

---

## Блок 2. Manual Migration Points (Тонкости PostgreSQL & Prisma)

Три архитектурных инварианта **не выражаются средствами Prisma ORM** и прописываются вручную через `raw SQL` в миграциях.

### 1. Порядок фаз и DEFERRABLE уникальность (`Phase.order`)

- **Проблема:** При изменении порядка колонок (драг-н-дроп) в Prisma происходит цепочка `UPDATE`. Если меняем местами 1-ю и 2-ю колонку, в момент выполнения запроса Postgres выбросит ошибку `Unique constraint failed`, так как временно образуются две колонки с `order = 2`.
- **Решение:** В PostgreSQL используется декларация `UNIQUE (workspaceId, order) DEFERRABLE INITIALLY DEFERRED`. Это говорит базе: _«Не проверяй уникальность на каждом отдельном UPDATE, проверь её только один раз при завершении транзакции (на COMMIT)»_. Prisma не умеет это генерировать, поэтому инвариант создается вручную.

### 2. Индексы под горячие кастомные поля (`Project.fields`)

- **Проблема:** Произвольные пользовательские поля хранятся в `JSONB`. Фильтрация и поиск по диапазонам (`budget > 5000`) внутри JSONB работают медленно на больших объемах.
- **Решение:** Для доказанно «горячих» полей в PostgreSQL через Raw SQL создаются **materialized / STORED generated columns** (материализованные, физически лежат на диске) с классическими `B-Tree` индексами прямо поверх JSONB.

### 3. Иммутабельность истории (`ActivityEvent`)

- **Проблема:** История событий должна быть строго защищена от изменений и случайного удаления (даже из-за багов в коде приложения).
- **Решение:** На уровне PostgreSQL у роли базы данных, которую использует приложение, полностью **отбираются права на `UPDATE` и `DELETE`** для таблицы `ActivityEvent`. В эту таблицу можно только делать `INSERT` и `SELECT`.

# Helix — Архитектурная карта сущностей и их зон ответственности

> **Как читать карту:** Система построена по принципу иерархической мультиарендности (Multi-tenancy).
> Каждая сущность имеет строго очерченную зону ответственности и правила удаления (onDelete).

---

## 1. Слой Изоляции и Пользователей (Tenant & Identity)

[ Organization ] ──── (1:N) ────> [ Membership ] <──── (N:1) ──── [ User ]
│ │
├─────── (1:N) ──────────> [ WorkspaceMember ] <───────────────┘
│
└─────── (1:N) ──────────> [ Workspace ]

- **`Organization` (Организация / Tenant)**
  - **Ответственность:** Верхнеуровневая граница изоляции данных. Вся система и каждый SQL-запрос фильтруются по `orgId`. Хранит глобальные настройки (валюта по умолчанию, брендинг, AI-провайдер) и тарифный план.
- **`User` (Пользователь)**
  - **Ответственность:** Физический аккаунт человека (email, хеш пароля / SSO). Может состоять в нескольких организациях одновременно.
- **`Membership` (Роль в Организации)**
  - **Ответственность:** Глобальный уровень доступа пользователя в рамках `Organization` (`OWNER`, `ADMIN`, `MANAGER`, `MEMBER`, `VIEWER`).

---

## 2. Слой Воронки и Настроек (Workspace & Blueprint)

[ Workspace ] ─── (1:N) ───> [ Phase ] (Колонки доски)
│
├─── (1:N) ───> [ FieldDefinition ] (Схема custom-полей)
└─── (1:N) ───> [ WorkspaceMember ] (Локальные переопределения прав)

- **`Workspace` (Воркспейс / CRM-доска)**
  - **Ответственность:** Конкретная воронка продаж или управления (например, _«Продажи B2B»_). Управляет своими колонками (`Phase`), схемой пользовательских полей и локальным составом команды.
- **`WorkspaceMember` (Права в воркспейсе)**
  - **Ответственность:** Переопределяет роль пользователя для конкретной доски и задает видимость записей (`visibility: ALL | ASSIGNED`).
- **`Phase` (Колонка / Этап)**
  - **Ответственность:** Этап воронки (например, _Discovery_). Содержит иммутабельный `key` (опора автоматизаций), порядок `order` (DEFERRABLE инвариант) и тип `PhaseType` (`OPEN`, `WON`, `LOST`).
- **`FieldDefinition` (Определение кастомных полей)**
  - **Ответственность:** Схема кастомных полей для карточек воркспейса (тип, метка, обязательность).
- **`Blueprint` (Шаблон воронки)**
  - **Ответственность:** Отчуждаемый JSON-шаблон (B2B/B2C) для быстрого создания готового `Workspace`. При использовании **копируется**, а не связывается живой ссылкой.

---

## 3. Ядро CRM — Сделка как Проект (Core Project Model)

                   [ Company ]
                        │ (1:N)
                        ▼

[ Phase ] ── (1:N) ──> [ Project ] <── (N:M) ── [ Contact ]
│ │ │
┌──────────────────┼──┴──┴──────────────────┐
▼ ▼ ▼
[ Task ] [ ProjectAssignee ] [ ActivityEvent ]

- **`Project` (Лид-как-Проект — Главная сущность)**
  - **Ответственность:** Карточка лида и одновременно его рабочее пространство. Хранит бюджет, статус (`status`), закрытый JSON с кастомными полями (`fields`), главного владельца (`ownerId`) и привязку к фазе.
- **`ProjectContact` (Таблица связи Лид ↔ Контакт)**
  - **Ответственность:** Связывает `Project` с физическими людьми (`Contact`). Хранит массив ролей человека именно в этой сделке (`roles: ["decision-maker", "champion"]`).
- **`ProjectAssignee` (Участники проекта)**
  - **Ответственность:** Список назначенных сотрудников (исполнителей/наблюдателей), работающих над карточкой.
- **`Task` (Высокоуровневая задача)**
  - **Ответственность:** Чек-лист внутри лида (заголовок, исполнитель, срок, `done`). Без сабтасков и спринтов (не Jira).

---

## 4. Слой Клиентов (B2B & B2C Contacts)

[ Company ] (Компания/Юрлицо) ──── (1:N) ────> [ Contact ] (Физлицо)

- **`Company` (Компания / B2B)**
  - **Ответственность:** Юридическое лицо (название, домен, отрасль).
- **`Contact` (Контакт / Физлицо)**
  - **Ответственность:** Данные конкретного человека (имя, email, телефон). Единственное место хранения PII-данных (для удобного выполнения требований GDPR). В B2C привязывается к `Project` напрямую, в B2B — через `Company`.

---

## 5. Аудит, История и AI (Event Log & RAG)

[ Project ] ─── (1:N, Append-Only) ───> [ ActivityEvent ] (Лента событий)
│
└──> [ payload: JSON ]
(Снапшот: P2 + P3)

- **`ActivityEvent` (Лента событий и Аудит)**
  - **Ответственность:** Неизменяемый (append-only) журнал всех действий по проекту. Инвариант P2 (хранит снапшот имен и ключей в `payload`), P3 (минимальный объем) и P4 (пишется атомарно в транзакции бизнеса). Защищен от UPDATE/DELETE на уровне Postgres.

---

## Дополнительные сущности (Появляются на вехах M3–M5)

- **`Page` / `KBArticle` (M3):** Rich-text документы внутри проекта и статьи базы знаний организации.
- **`Attachment` (M3):** Загруженные файлы (PDF, Docx), привязанные к S3/MinIO.
- **`EmbeddingChunk` (M4):** Векторизованные кусочки текста из страниц и файлов (`pgvector`) для работы RAG (Talk-to-Project AI).
- **`ApiKey` / `Webhook` (M5):** Ключи доступа для внешних систем (прием лидов) и исходящ
